## 8.1 入出力の基本問題

### 速度差という現実

第2回・第5回・第6回で見た遅延を、もう一度並べる。

| 対象 | 時間 | CPU の1サイクルを1秒とすると |
| --- | ---: | --- |
| CPU の1サイクル | 0.3 ns | 1秒 |
| 主記憶 | 80 ns | 4分 |
| NVMe SSD | 20 µs | **18時間** |
| HDD（ランダム） | 12 ms | **1年3ヶ月** |
| ネットワーク（国内往復） | 20 ms | 2年 |
| キーボードの1打鍵 | 100 ms 以上 | **10年以上** |

CPU から見れば、周辺装置は**止まっているに等しい**。

もし CPU が「装置が終わるまで待つ」設計だったら、
計算機の時間の99.99%以上が待機に費やされる。
入出力の仕組みの全体が、**この待ち時間をどう使うか**という問題への答えである。

### 方式1：ポーリング

もっとも素朴な方法は、CPU が装置の状態を繰り返し確認することである。

```
while (装置の状態レジスタ != 準備完了) {
    ;   /* 何もせずに聞き続ける */
}
データを読む
```

これを**ポーリング**（あるいはビジーウェイト）という。

- **利点** — 単純。応答が速い（準備完了を即座に検知できる）
- **欠点** — 待っている間、CPU が丸ごと無駄になる

キーボード入力をポーリングで待つと、
利用者がキーを押すまでの間、CPU は全力で「まだか、まだか」と
聞き続けることになる。

**ポーリングが適する場面もある。** 待ち時間がごく短いと分かっている場合
（高速な NVMe SSD、10Gbps を超えるネットワーク）では、
次の割り込み方式のオーバヘッドのほうが大きくなるため、
あえてポーリングする設計が使われる。

### 方式2：割り込み

**割り込み** (interrupt) は発想を逆転させる。

> CPU が装置に聞きに行くのではなく、**装置が終わったときに CPU に知らせる。**

CPU は入出力を依頼したら、そのプロセスを待機状態にして
（第7回の Blocked）、**別のプロセスを実行する**。
装置から信号が来たら、そこで初めて対応する。

これで待ち時間が有効に使える。第7回で見た多重プログラミングは、
割り込みがあって初めて成立する。

### 割り込み発生時の動作

> **[図 8-1] 割り込み処理の流れ**
> 横軸を時間として、上段に「CPU が実行している内容」の帯を描く。
> プロセスA実行中 → （割り込み信号↓）→ 退避 → ハンドラ実行 → 復元 →
> プロセスA再開、と区切る。
> 下段に周辺装置の帯を置き、装置が独立に動作している期間と、
> 完了時に上向きの矢印で割り込み信号を送る様子を描く。
> 「CPU と装置が同時に動いている」ことが一目で分かるようにする。

![図 8-1 割り込み処理の流れ](../figures/fig-08-01.svg)

1. 装置が割り込み信号を送る
2. CPU が現在の命令を完了する（命令の途中では止まらない）
3. **現在の状態（PC、レジスタ、フラグ）を退避する**
4. 特権モードに切り替わる
5. **割り込みベクタ表**を引いて、割り込みの種類に対応する
   **ハンドラ**（処理ルーチン）の番地を得る
6. ハンドラを実行する（データを受け取る、待っていたプロセスを Ready にする）
7. 状態を復元し、元のモードに戻り、中断した箇所から再開する

**(3) と (7) が肝である。** 割り込まれたプログラムは、
自分が中断されたことに気づかない。第7回のコンテキストスイッチと同じ仕組みが
ここでも働いている。

### 割り込みの種類

| 種類 | きっかけ | 例 |
| --- | --- | --- |
| 外部割り込み | 周辺装置から | 入出力完了、キー入力、ネットワーク受信 |
| タイマ割り込み | 時計から定期的に | **スケジューラが制御を取り戻す**（第7回） |
| 内部割り込み（例外） | 実行中の命令自体 | ゼロ除算、ページフォルト、不正な命令 |
| ソフトウェア割り込み | 命令で意図的に | システムコール（第7回） |

**タイマ割り込みの重要性**: これがなければ、
暴走したプログラムから OS が制御を取り戻せない。
第7回の「横取り式スケジューリング」は、タイマ割り込みの上に成り立っている。

**ページフォルトも割り込み**である。第5回で見た「必要なページが
主記憶にない」状態は、内部割り込みとして OS に通知され、
OS がページを読み込んでから、中断した命令をやり直す。

### 方式3：DMA

割り込みで待ち時間は解決した。しかしまだ問題がある。

**データの転送そのものを CPU が行っている。** 1MB のデータを
ディスクから主記憶へ移すのに、CPU が1ワードずつ読んでは書く、を
繰り返すことになる。せっかく割り込みで手が空いても、
転送で塞がってしまう。

**DMA** (Direct Memory Access) は、転送を専用のコントローラに任せる。

```
1. CPU が DMA コントローラに指示する
   （どの装置から、主記憶のどこへ、何バイト）
2. CPU は別の仕事に戻る
3. DMA コントローラが装置と主記憶の間で直接データを運ぶ
4. 転送が完了したら、DMA コントローラが CPU に割り込みをかける
```

CPU が関与するのは**最初の指示と最後の通知だけ**になる。

> **[図 8-2] CPU 経由の転送と DMA の比較**
> 上段に CPU 経由の転送を描く。装置→CPU→主記憶 と2本の矢印が CPU を経由し、
> その間 CPU の帯が「転送で占有」と塗られる。
> 下段に DMA を描く。装置→主記憶 の矢印が DMA コントローラを介して直接つながり、
> CPU の帯は「別の処理」と塗られる。両者で CPU の空き時間の差を示す。

![図 8-2 CPU 経由の転送と DMA の比較](../figures/fig-08-02.svg)

現代の周辺装置（NVMe SSD、ネットワークカード、GPU）はすべて DMA を使う。

### 入出力をシステムコール経由にする理由

アプリケーションが装置を直接触れないことは第7回で見た。
入出力に限って、その利点をもう一度整理する。

| 利点 | 内容 |
| --- | --- |
| 装置の違いを隠せる | HDD でも SSD でも USB メモリでも `read` で読める |
| 排他制御ができる | 複数プロセスの同時アクセスを OS が調停する |
| 権限を検査できる | 読む権利があるかを一箇所で確認できる |
| 効率化できる | 頻繁に読む内容をキャッシュに保持できる |
| 抽象を統一できる | Unix の「すべてはファイル」——装置もパイプもソケットも同じ操作で扱える |

## 8.2 デバイスドライバと入出力装置

### デバイスドライバ

**デバイスドライバ**は、特定の装置の扱い方を知っているソフトウェアで、
カーネルの一部として動く。

```
アプリケーション
   ↓ read() システムコール
カーネル（統一されたインタフェース）
   ↓
デバイスドライバ（装置固有の作法）
   ↓
ハードウェア
```

この層があるおかげで、新しい装置が出ても
**アプリケーションを書き直さずに済む**。ドライバだけ追加すればよい。

これも「契約を決めて中身を差し替え可能にする」構図である
（第3回の ISA、第4回のリンク、第6回のファイルシステム）。

**ドライバはカーネル空間で動く**ため、バグがあるとシステム全体が落ちる。
Windows のブルースクリーンの多くはドライバに起因する。
このため、ドライバをユーザ空間で動かす設計（マイクロカーネル）も研究されている。

### 主な入出力装置の原理

装置の種類は多いが、**原理の型はいくつかしかない**。
代表例を押さえておけば、新しい装置も理解できる。

**入力：物理量を電気信号にする**

| 装置 | 原理 |
| --- | --- |
| キーボード | 格子状の配線を走査し、押された交点を検出する（キーマトリクス） |
| 光学式マウス | 表面を高速で撮像し、直前の画像との**ずれ**から移動量を算出する |
| 静電容量式タッチパネル | 指が近づくと変化する電極間の静電容量を検出する |
| イメージセンサ | 光電効果で光を電荷に変え、電荷量を数値化する（CCD / CMOS） |

**出力：電気信号を物理量にする**

| 装置 | 原理 |
| --- | --- |
| 液晶ディスプレイ | 電圧で液晶分子の向きを変え、偏光板を通る光量を制御する。自ら光らずバックライトが要る |
| 有機EL (OLED) | 素子自体が発光する。バックライトが不要で、黒を完全に消せる |
| レーザープリンタ | 感光体に静電潜像を描き、トナーを付着させて紙に転写・定着する |
| インクジェットプリンタ | 熱またはピエゾ素子でインクの液滴を飛ばす |

> **[図 8-3] キーマトリクスによるキー検出**
> 縦横の配線が格子状に交差する図を描き、交点にスイッチを置く。
> 横の配線を1本ずつ順に通電し、縦の配線のどれに電流が現れるかで
> 押された交点を特定する走査の様子を、3ステップの連続図で示す。
> 「n×m 個のキーを n+m 本の配線で読める」という要点を注記する。

![図 8-3 キーマトリクスによるキー検出](../figures/fig-08-03.svg)

**キーマトリクスの要点**は配線数である。104個のキーに1本ずつ線を引けば
104本要るが、格子にすれば 8×13 = 21本で済む。
**走査という時間の使い方で、空間（配線）を節約している。**
計算機科学に繰り返し現れる時間と空間のトレードオフである。

### 接続インタフェース

装置と計算機をつなぐ規格。2026年時点で現役のものに絞る。

| 規格 | 用途 | 速度の目安 |
| --- | --- | --- |
| USB 3.2 / USB4 | 汎用周辺機器 | 20 Gbps / 40 Gbps |
| Thunderbolt 4 / 5 | 高速周辺機器、映像 | 40 Gbps / 80 Gbps |
| PCI Express 5.0 | 内部拡張（GPU、NVMe SSD） | レーンあたり 32 GT/s |
| HDMI 2.1 / DisplayPort 2.1 | 映像出力 | 48 Gbps / 80 Gbps |
| Ethernet (1G/10G/100G) | 有線ネットワーク | 第9回で扱う |
| Wi-Fi 6E / 7 | 無線ネットワーク | 第9回で扱う |

**USB Type-C とオルタネートモード**: Type-C は**コネクタの形状**の規格であり、
そこを流れるプロトコルは別である。同じ形の端子で USB、DisplayPort、
Thunderbolt、電力供給（最大240W）が扱える。
「挿さるのに動かない」という混乱の原因はここにある。

**歴史的な規格**（IDE/ATA、SCSI、RS-232C、パラレルポート、PS/2、VGA）は、
現行の機器ではほぼ見かけない。ただし RS-232C は産業機器や
ネットワーク機器の保守用コンソールとして今も使われており、
「単純で確実な通信路」が必要な場面では現役である。

## 8.3 仮想化とコンテナ

### 抽象化をもう一段上げる

ここまでで、OS は次の抽象を提供してきた。

- 物理メモリ → 仮想アドレス空間（第5回）
- ブロックの列 → ファイル（第6回）
- 1個の CPU → 複数のプロセス（第7回）
- 個々の装置 → 統一されたインタフェース（8.2）

**次の一手は、「計算機そのもの」を抽象化することである。**

### 仮想化

**仮想化**とは、1台の物理計算機の上に、複数の「仮想的な計算機」を作る技術である。
各仮想機械 (VM) は、独立した OS を持ち、自分専用のハードウェアがあると信じている。

これを実現するソフトウェアを**ハイパーバイザ**という。

| 型 | 構成 | 例 |
| --- | --- | --- |
| Type 1（ベアメタル） | ハードウェアの上で直接動く | KVM, Xen, VMware ESXi, Hyper-V |
| Type 2（ホスト型） | ホスト OS の上で動く | VirtualBox, VMware Workstation |

**なぜ動くのか**: ゲスト OS は特権命令を実行しようとする。
しかしゲスト OS 自身は非特権モードで動いているため、
命令が実行されずハイパーバイザに制御が渡る。
ハイパーバイザが代わりに処理して、あたかも成功したかのように見せる。

現代の CPU には仮想化支援機能（Intel VT-x、AMD-V、Arm の仮想化拡張）があり、
この切り替えをハードウェアで高速に行う。
第5回で見たページテーブルも、仮想化では2段階になる
（ゲストの仮想→ゲストの物理→ホストの物理）。

**得られるもの**:

- **集約** — 使用率の低いサーバを1台に集められる
- **分離** — 1つの VM が落ちても他は無事
- **可搬性** — VM はファイルなので、別の物理サーバへ移せる（ライブマイグレーション）
- **柔軟性** — 必要なときに作り、不要になったら消せる

**この4つが、そのままクラウドの技術的基礎になる。**

### コンテナ

仮想機械には無駄がある。**OS を丸ごと複製している**ことである。

同じ Linux 上で10個の Web アプリを動かしたいだけなのに、
VM を10個作ると、Linux カーネルが10個動き、
それぞれが数 GB のメモリと数十秒の起動時間を消費する。

**コンテナ**は、**カーネルは1つを共有したまま、
プロセスから見える世界だけを分離する**。

> **[図 8-4] 仮想機械とコンテナの構成比較**
> 左に仮想機械の積層図：ハードウェア → ハイパーバイザ →
> 「ゲストOS＋ライブラリ＋アプリ」の箱を3つ。
> 右にコンテナの積層図：ハードウェア → ホストOS（カーネル） →
> コンテナランタイム → 「ライブラリ＋アプリ」の箱を3つ。
> 右ではゲストOSの層が消えていることを、箱の高さの差で示す。

![図 8-4 仮想機械とコンテナの構成比較](../figures/fig-08-04.svg)

| | 仮想機械 | コンテナ |
| --- | --- | --- |
| 分離するもの | ハードウェア | プロセスの名前空間と資源 |
| カーネル | ゲストごとに1つ | **ホストのものを共有** |
| 起動時間 | 数十秒 | **1秒未満** |
| メモリ消費 | GB 単位 | MB 単位 |
| 分離の強度 | **強い** | 中程度（カーネルの脆弱性は共有される） |
| 異なる OS | 動かせる | **動かせない**（Linux 上では Linux のみ） |

コンテナを支える Linux カーネルの機能:

- **名前空間 (namespace)** — プロセス番号、ファイルシステム、
  ネットワーク、ホスト名などを、コンテナごとに別々に見せる
- **cgroups** — CPU、メモリ、入出力の使用量に上限を設ける
- **重ね合わせファイルシステム** — 共通部分を共有し、
  差分だけを各コンテナが持つ

**コンテナイメージ**は、アプリケーションとその依存関係
（ライブラリ、設定）を1つにまとめたものである。
「開発環境では動くのに本番で動かない」という古典的な問題を、
**環境ごと持ち運ぶ**ことで解決する。

**オーケストレーション**: コンテナが数百・数千になると、
どのサーバでどれを動かすか、落ちたらどう再起動するか、
負荷に応じてどう増減するかを人手で管理できない。
これを自動化するのが Kubernetes などのオーケストレータである。

**選び分け**: 強い分離が要るとき（異なる顧客のワークロード、
信頼できないコードの実行）は仮想機械、
自分たちのアプリを効率よく多数動かすときはコンテナ、
というのが基本である。両者は排他ではなく、
クラウドでは「VM の中でコンテナを動かす」構成が一般的である。

## 8.4 クラウドコンピューティング

### 何が変わったのか

**クラウドコンピューティング**とは、
計算資源をネットワーク越しに、必要な分だけ、使った分だけ払って利用する形態である。

技術的には 8.3 の仮想化とコンテナの上に立つ。
しかし本質的な変化は技術ではなく、**資源の扱い方**にある。

| | 自前で持つ（オンプレミス） | クラウド |
| --- | --- | --- |
| 調達 | 見積り・発注・搬入・設置に数週間〜数ヶ月 | **数分** |
| 費用の性質 | 設備投資（先に大きく払う） | 経費（使った分だけ） |
| 容量の決め方 | ピークに合わせて買う | **需要に応じて増減** |
| 失敗のコスト | 買った機材が無駄になる | 消せば止まる |

**ピークに合わせて買う**ことの無駄は大きい。
たとえば履修登録システムは、年に数日だけ極端な負荷がかかり、
残りの360日は遊んでいる。自前なら最大負荷に合わせた設備が
1年中遊ぶことになる。クラウドなら必要な日だけ増やせる。

**もっとも重要な変化は、失敗のコストが下がったこと**である。
「試してみて、駄目ならやめる」が数千円でできるようになった。
これがスタートアップや新規事業の在り方そのものを変えた。

### サービスモデル

どこまでを事業者に任せるかで段階がある。

> **[図 8-5] サービスモデルと責任分界**
> 縦に「アプリケーション／データ／ランタイム／ミドルウェア／OS／
> 仮想化／サーバ／ストレージ／ネットワーク／施設」の層を積んだ柱を4本並べる。
> 左からオンプレミス、IaaS、PaaS、SaaS。
> 各柱で「利用者の責任」と「事業者の責任」を塗り分け、
> 境界線が右へ行くほど上に上がっていく様子を示す。

![図 8-5 サービスモデルと責任分界](../figures/fig-08-05.svg)

| モデル | 事業者が管理 | 利用者が管理 | 例 |
| --- | --- | --- | --- |
| IaaS | 施設・機材・仮想化 | OS より上すべて | 仮想サーバ、仮想ネットワーク |
| PaaS | OS・実行環境まで | アプリとデータ | アプリ実行基盤、マネージドDB |
| SaaS | ほぼすべて | データと設定のみ | メール、表計算、業務アプリ |
| FaaS（サーバレス） | 実行基盤すべて | 関数のコードのみ | イベント駆動の関数実行 |

### 責任共有モデル

**「クラウドを使えば安全」は誤りである。**
事業者と利用者の間で責任が分担されている。

| 事業者の責任 | 利用者の責任 |
| --- | --- |
| データセンタの物理的安全 | アクセス権限の設定 |
| ハードウェアの保守 | データの暗号化と分類 |
| ハイパーバイザの安全性 | OS とアプリの更新（IaaS の場合） |
| （SaaS では）アプリの安全性 | **利用者アカウントの管理** |

**現実の情報漏洩の多くは、事業者側ではなく利用者側の設定ミス**による。
「ストレージを誤って全世界に公開していた」「権限を過剰に与えていた」
という事例が繰り返されている。第12回で改めて扱う。

### 技術的な利点

| 利点 | 内容 |
| --- | --- |
| 弾力性 | 負荷に応じて自動的に増減する |
| 可用性 | 複数のデータセンタに分散し、1箇所が落ちても継続する |
| 到達速度 | 世界中の拠点から配信できる（第10回の CDN） |
| 保守の委譲 | ハードウェアの故障対応、OS の更新を任せられる |
| 実験の容易さ | 試して壊して作り直せる |

### 暗黒面

利点だけを見るのは危険である。

| 課題 | 内容 |
| --- | --- |
| **ベンダロックイン** | 特定事業者固有のサービスに依存すると、移行が事実上不可能になる |
| **障害の巻き添え** | 事業者の障害で、無関係な多数のサービスが同時に止まる |
| **費用の逆転** | 使用量が安定して大きい場合、自前のほうが安くなることがある |
| **費用の予測困難** | 従量課金は、設定ミスや攻撃で請求が跳ね上がりうる |
| **データの所在** | 法域をまたぐデータ保管が、法規制（GDPR、個人情報保護法）に抵触しうる |
| **可視性の低下** | 内部で何が起きているか分からない。問題の切り分けが難しい |
| **サービス終了** | 事業者の都合で機能が廃止される |

**大規模な事業者ほど、障害の影響範囲が広い**という構造的な問題がある。
1つのクラウドの1つの地域が停止すると、金融、交通、通信、行政まで
同時に影響を受ける事態が現実に起きている。
効率のための集中が、社会全体の脆弱性になっている。

対策としては、複数事業者の併用、自前とクラウドの組み合わせ（ハイブリッド）、
移行可能な技術の選択（コンテナや標準的な API を使い、
事業者固有の機能への依存を減らす）が挙げられる。

## まとめ

- 周辺装置は CPU から見れば止まっているに等しい。
  入出力の仕組みは、この待ち時間をどう使うかへの答えである
- ポーリングは単純だが CPU を浪費する。割り込みは装置側から知らせることで
  待ち時間を他の処理に使えるようにする
- 割り込みでは状態を退避し、ハンドラを実行し、復元して再開する。
  割り込まれた側は中断に気づかない
- タイマ割り込みが OS の制御権を保証し、横取り式スケジューリングを成り立たせる
- DMA は転送そのものを専用コントローラに任せ、CPU を解放する
- デバイスドライバが装置ごとの差を吸収し、統一されたインタフェースを保つ
- 仮想化は計算機そのものを抽象化する。コンテナはカーネルを共有し、
  より軽量に分離する
- クラウドの本質は技術ではなく、調達の速さと失敗コストの低下にある。
  ただし責任は共有であり、ロックインと集中リスクを伴う
