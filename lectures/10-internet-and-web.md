## 10.1 トランスポート層：TCP と UDP

### 何を担うのか

IP は「どこかのホストまで」届ける（第9回 9.5）。しかし足りないものがある。

- 同じホスト上のどのアプリケーション宛か（**ポート番号**）
- 失われたパケットの再送、順序の復元（**信頼性**）
- 送りすぎて相手や網を溢れさせない制御（**フロー制御・輻輳制御**）

トランスポート層がこれを担う。

### ポート番号

16ビットの番号（0〜65535）で、ホスト内のアプリケーションを識別する。

通信の端点は、次の**5つ組**で一意に定まる。

```
(プロトコル, 送信元IP, 送信元ポート, 宛先IP, 宛先ポート)
```

これにより、1台のサーバが同時に多数のクライアントと通信できる。

**よく使われるポート番号**:

| 番号 | サービス |
| ---: | --- |
| 22 | SSH |
| 25 | SMTP（メール配送） |
| 53 | DNS |
| 80 | HTTP |
| 443 | HTTPS |

0〜1023 は**ウェルノウンポート**で、多くの OS では
特権が必要である（勝手に偽のサービスを立てられないようにするため）。

### プログラムから見た通信：ソケット

ここまではプロトコルの側から見てきた。
**プログラムを書く側から見ると、通信はどう見えるのか。**

答えは**ソケット**である。ソケットは通信の端点を表す抽象で、
アプリケーションからは**ファイル記述子**として扱える（第7回）。
つまり、いったん接続してしまえば `read` / `write` で読み書きできる。
相手がファイルなのかパイプなのか地球の裏側のサーバなのかを、
プログラムは意識しなくてよい。

サーバとクライアントで、呼ぶシステムコールの並びが違う。

> **[図 10-1] ソケットの呼び出し順序（TCP）**
> 左にサーバ、右にクライアントの縦の流れを並べる。
> サーバ側は socket → bind → listen → accept →（read / write の往復）→ close、
> クライアント側は socket → connect →（write / read の往復）→ close を
> 上から順に箱で置く。
> accept と connect の間を「接続の確立（3ウェイハンドシェイク）」の線で結び、
> read/write の区間を両向きの矢印で結ぶ。
> accept が「接続を待って止まる」ことと、accept が**新しいソケットを返す**ため
> 元のソケットで次の接続を待ち続けられることを、右側に注記する。

![図 10-1 ソケットの呼び出し順序（TCP）](../figures/fig-10-01.svg)

| 呼び出し | すること |
| --- | --- |
| `socket` | 通信の口を作る。TCP なら `SOCK_STREAM`、UDP なら `SOCK_DGRAM` |
| `bind` | 自分のアドレスとポート番号をソケットに結びつける |
| `listen` | 接続要求を受け付ける状態にする（サーバのみ） |
| `accept` | 接続要求が来るまで待ち、**新しいソケット**を返す（サーバのみ） |
| `connect` | 相手に接続を要求する（クライアントのみ） |
| `read` / `write` | データをやりとりする。ファイルと同じ操作 |
| `close` | 切断する |

**`accept` が新しいソケットを返す**ことが要点である。
元のソケットは接続待ち専用として残るので、
サーバは1つの受付口で何千もの接続を同時に扱える。
第7回で見た `fork` やスレッドと組み合わせれば、
接続ごとに処理を分けられる。

**通信の端点は5つ組で決まる**（10.1 の冒頭で述べたとおり）ので、
同じサーバの同じポートに多数のクライアントが接続しても、
送信元の IP とポートが違うため取り違えない。

**現代的な注意**: 昔の教材は `sockaddr_in` 構造体を手で埋め、
バイト順序を変換する手順を載せていた。
これは IPv4 を前提とした書き方で、現在は **`getaddrinfo`** を使う。
名前からアドレスを引き、IPv4 と IPv6 のどちらでも同じコードで扱える。
実際のアプリケーションでは、この層を直接触ることはまれで、
ライブラリやフレームワークが包んでいる。

それでも**この5〜6個のシステムコールが土台にある**ことは知っておくとよい。
「なぜポート番号が要るのか」「なぜサーバは待ち受けるのか」
「なぜ接続がタイムアウトするのか」——いずれもこの層で起きている。

### UDP

**UDP** (User Datagram Protocol) は、IP にポート番号と
簡単な誤り検出を足しただけの、極めて薄い層である。

- コネクションを張らない
- 再送しない、順序を保証しない、到着を保証しない
- ヘッダは8バイトと小さい
- 送りたいときに送るだけなので**遅延が小さい**

**「保証しない」ことが利点になる場面がある。**

- **音声・映像のリアルタイム通信** — 1つ前のパケットが遅れて届いても、
  もう再生時刻を過ぎている。再送は無駄であり、
  待つことで会話全体が遅れるほうが害が大きい
- **DNS の問い合わせ** — 1往復で終わる。コネクション確立の手間が
  データ本体より大きい
- **一斉配信** — 多数の相手に同じデータを流す

### TCP

**TCP** (Transmission Control Protocol) は、
**ベストエフォートの上に信頼性を作る**。

| 保証すること | 仕組み |
| --- | --- |
| 到達 | 確認応答 (ACK) と再送 |
| 順序 | シーケンス番号で並べ直す |
| 重複の除去 | シーケンス番号で判定 |
| 誤りの検出 | チェックサム |
| 溢れさせない | ウィンドウ制御 |
| 網を詰まらせない | 輻輳制御 |

**信頼性は下の層が提供するのではなく、端点どうしが作る。**
これはインターネットの設計思想（エンド・ツー・エンド原理）そのものである。
網の中身は単純に保ち、賢さは端点に置く。だから網は速く、
新しいアプリケーションを網の改修なしに導入できる。

### コネクションの確立：3ウェイハンドシェイク

> **[図 10-2] 3ウェイハンドシェイクと切断**
> 左にクライアント、右にサーバの縦線を引き、時間を下向きに取る。
> SYN（seq=x）→ SYN+ACK（seq=y, ack=x+1）→ ACK（ack=y+1）の
> 3本の斜め矢印を描く。その下にデータ転送を示し、
> さらに下に FIN → ACK → FIN → ACK の4ウェイの切断を描く。
> 「3往復半ではなく1.5往復で確立する」ことを注記する。

![図 10-2 3ウェイハンドシェイクと切断](../figures/fig-10-02.svg)

1. クライアント → サーバ: **SYN**（接続したい。私の開始番号は x）
2. サーバ → クライアント: **SYN + ACK**（了解。私の開始番号は y。x+1 を待つ）
3. クライアント → サーバ: **ACK**（了解。y+1 を待つ）

**なぜ3回なのか。** 双方が「自分の開始番号を伝える」ことと
「相手の開始番号を受け取った」ことを確認する必要があり、
2番目のメッセージで2つを兼ねられるので、最小で3回になる。

**代償**: データを送り始める前に**1往復（RTT）が必要**である。
東京とヨーロッパの間なら約 250ms。この待ち時間が、
後述する QUIC の動機になる。

### 再送と順序の復元

- 送信側はデータに**シーケンス番号**を付けて送る
- 受信側は受け取った範囲を **ACK** で知らせる
- 一定時間 ACK が来なければ**再送**する
- 受信側は番号順に並べ直してからアプリケーションに渡す

**順序の復元がある**ため、アプリケーションは
パケットが入れ替わったことを知らない。
第9回で「下の層が保証しないことを上の層が補う」と述べたのがこれである。

### フロー制御と輻輳制御

**フロー制御**は、**受信側が処理しきれない量**を送らないようにする。
受信側が「あと何バイト受け取れるか」（ウィンドウサイズ）を
ACK に載せて伝え、送信側はそれを超えて送らない。

**輻輳制御**は、**網が詰まらないようにする**。
こちらのほうが難しい。網の混雑具合は直接観測できないためである。

TCP は「パケットが失われた＝網が混んでいる」と解釈し、
送信量を調整する。

```
1. 少量から始め、うまく届くたびに送信量を増やす（スロースタート）
2. パケット損失を検知したら、送信量を大きく減らす
3. また徐々に増やす
```

**この仕組みが、インターネット全体を破綻から守っている。**
各端点が自主的に遠慮するだけで、中央の管理なしに公平な帯域配分が成立する。
1986年に実際に発生した輻輳崩壊（網が混雑し、再送がさらに混雑を呼び、
実効スループットが1/1000に落ちた事件）の教訓から作られた。

### 使い分け

| | TCP | UDP |
| --- | --- | --- |
| 保証 | あり | なし |
| コネクション | 必要 | 不要 |
| 遅延 | 確立と再送の分だけ増える | 小さい |
| ヘッダ | 20バイト以上 | 8バイト |
| 主な用途 | Web、メール、ファイル転送 | 音声・映像通話、DNS、ゲーム |

## 10.2 名前解決：DNS

### 何のためにあるか

人間は `203.0.113.42` を覚えられない。`www.example.com` なら覚えられる。
**DNS** (Domain Name System) は、この名前を IP アドレスに変換する。

さらに重要な役割がある。**名前とアドレスを分離すること**である。
サーバを別のデータセンタに移しても、DNS の記録を書き換えれば
利用者は同じ名前でアクセスできる。

### 階層構造

ドメイン名は右から左へ階層をなす。

```
www . example . com .
 |      |        |   └─ ルート
 |      |        └───── トップレベルドメイン (TLD)
 |      └────────────── 第2レベル
 └───────────────────── ホスト名
```

管理も階層的に委譲されている。ルートは TLD の管理者を知っており、
TLD は各ドメインの管理者を知っている。
**誰も全体を知らないが、たどれば必ず答えに着く。**
第9回のインターネットの構造と同じ、非中央集権の設計である。

### 名前解決の流れ

> **[図 10-3] 反復問い合わせによる名前解決**
> 左にクライアント、その右にキャッシュDNSサーバ（フルリゾルバ）、
> 右側に上からルートDNS、`.com` のDNS、`example.com` のDNS を縦に並べる。
> クライアント→リゾルバ の1本の矢印（再帰問い合わせ）と、
> リゾルバから3つのサーバへの往復矢印（反復問い合わせ）を番号付きで描く。
> 各往復で得られる回答（「.com はあちらに聞け」「example.com はあちらに聞け」
> 「答えは 203.0.113.42」）を吹き出しで添える。

![図 10-3 反復問い合わせによる名前解決](../figures/fig-10-03.svg)

1. クライアントが**キャッシュ DNS サーバ**に `www.example.com` を問う
2. キャッシュサーバがルート DNS に問う → 「`.com` の担当はここ」
3. `.com` の DNS に問う → 「`example.com` の担当はここ」
4. `example.com` の DNS に問う → 「`www` は 203.0.113.42」
5. クライアントに答え、**一定時間キャッシュする**（TTL）

キャッシュがあるので、実際にはほとんどの問い合わせが1〜2段階で終わる。

### DNS の重要性と脆さ

DNS が止まると、サーバが正常でも**誰もたどり着けない**。
大規模なサービス障害の原因が DNS であることは珍しくない。

また、DNS は元来、通信内容が暗号化されておらず、
**誰がどこを見ているかが傍受でき、応答を偽装できる**という問題があった。
偽の応答を返して利用者を偽サイトへ誘導する攻撃（DNS キャッシュポイズニング）が
実際に行われている。

対策として次が普及しつつある。

- **DNSSEC** — 応答に署名を付け、改竄を検知する
- **DoH / DoT** — DNS の問い合わせ自体を HTTPS/TLS で暗号化する

## 10.3 HTTP と TLS

### HTTP

**HTTP** (HyperText Transfer Protocol) は、Web の通信規約である。
基本は単純で、**クライアントが要求し、サーバが応答する**。

要求の例:

```
GET /index.html HTTP/1.1
Host: www.example.com
User-Agent: ...
Accept: text/html
```

応答の例:

```
HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Content-Length: 1234

<!DOCTYPE html>...
```

**主なメソッド**:

| メソッド | 意味 |
| --- | --- |
| GET | 取得する（副作用を持たせてはならない） |
| POST | 送信する（新規作成、処理の実行） |
| PUT | 置き換える |
| DELETE | 削除する |

**主なステータスコード**:

| 番号 | 意味 |
| ---: | --- |
| 200 | 成功 |
| 301 / 302 | 移動した（恒久 / 一時） |
| 400 | 要求が不正 |
| 401 / 403 | 認証が必要 / 権限がない |
| 404 | 見つからない |
| 500 | サーバ内部のエラー |
| 503 | 一時的に処理できない |

**ステートレス**であることが HTTP の設計上の特徴である。
サーバは要求と要求の間の状態を覚えていない。
これによりサーバを増やして負荷分散するのが容易になる。
ログイン状態のような「覚えておきたいもの」は、
Cookie やトークンとして**クライアント側に持たせる**。

### HTTP の版

| 版 | 年 | 主な改良 | 下位のプロトコル |
| --- | ---: | --- | --- |
| HTTP/1.1 | 1997 | 1つの接続を使い回す（Keep-Alive） | TCP |
| HTTP/2 | 2015 | 多重化、ヘッダ圧縮、サーバプッシュ | TCP |
| HTTP/3 | 2022 | **QUIC 上で動く**、接続確立の高速化 | **UDP** |

**HTTP/1.1 の問題**: 1つの接続で1度に1つの要求しか処理できない。
先頭の要求が遅いと後続が待たされる（**ヘッドオブラインブロッキング**）。
ブラウザは接続を複数張って回避していたが、限界があった。

**HTTP/2 の改良**: 1つの接続の中で複数の要求を**多重化**する。
ただし下が TCP なので、パケットが1つ失われると
**TCP の層で**全ストリームが待たされる問題が残った。

**HTTP/3 と QUIC**: そこで **UDP の上に**、必要な機能を自前で実装した
**QUIC** というプロトコルを作った。

- ストリームごとに独立して再送するので、1つの損失が他を止めない
- 暗号化（TLS 1.3）が組み込まれており、
  **コネクション確立と暗号鍵の交換を同時に行う**（1往復、条件次第で0往復）
- IP アドレスが変わっても接続を維持できる（Wi-Fi から携帯網への切替で切れない）
- OS のカーネルではなくアプリケーション側で実装されるため、改良を展開しやすい

**「TCP の代わりを UDP の上に作る」**という一見奇妙な選択は、
TCP がカーネルと機器に深く根を張っていて改良できない、
という現実への対処である。

### TLS

**TLS** (Transport Layer Security) は、通信を暗号化するプロトコルである。
HTTP と組み合わせたものが **HTTPS** である。
（SSL は TLS の前身で、既に安全でない。呼び名として残っているが実体は TLS。）

TLS が保証するのは3つである。

| 保証 | 内容 |
| --- | --- |
| **機密性** | 第三者に内容を読まれない |
| **完全性** | 途中で書き換えられたら検知できる |
| **真正性** | 通信相手が名乗ったとおりの相手である |

**3つ目が最も重要である。** 暗号化しても、
暗号化した相手が偽サイトなら意味がない。
サーバ証明書によって「このサーバは確かに example.com である」ことを
確認する仕組みが要る。その中身は第12回で扱う。

2026年時点では **TLS 1.3** が標準である。
TLS 1.0/1.1 は廃止され、1.2 も設定によっては安全でない。

**HTTPS が当たり前になった**背景には、
無料で証明書を発行する仕組み（ACME プロトコルによる自動化）の普及がある。
かつては費用と手間がかかり、「重要なページだけ HTTPS」が普通だった。

## 10.4 Web アプリケーションと分散

### Web アプリケーションの構成

初期の Web は、あらかじめ用意された HTML ファイルを返すだけだった（静的）。
現在は、要求に応じて内容を組み立てて返す（動的）。

典型的な三層構成:

> **[図 10-4] Web アプリケーションの三層構成**
> 左からブラウザ、（インターネットを挟んで）ロードバランサ、
> Web/アプリケーションサーバ（複数台を縦に並べる）、
> データベース（1台＋レプリカ）を横に並べる。
> ロードバランサから複数のアプリサーバへ矢印が分岐し、
> それらが同じデータベースを指す構図を描く。
> 右上にキャッシュ層、左上に CDN を配置し、
> どの経路がどの層で応答を返しうるかを示す。

![図 10-4 Web アプリケーションの三層構成](../figures/fig-10-04.svg)

| 層 | 役割 |
| --- | --- |
| プレゼンテーション層 | 画面の表示。ブラウザ上の HTML/CSS/JavaScript |
| アプリケーション層 | 処理の実行。要求を受けて計算し、応答を作る |
| データ層 | データの永続化。データベース（第11回） |

**分離する理由**: 各層を独立に増やせる。
アクセスが増えたらアプリケーションサーバを増やし、
データが増えたらデータベースを強化する。

HTTP がステートレスであることが、
「アプリケーションサーバを何台に増やしてもよい」ことを可能にしている。

### API と通信形式

現代の Web では、画面を返すのではなく**データを返す**設計が主流である。

| 方式 | 特徴 |
| --- | --- |
| REST | 資源を URL で表し、HTTP メソッドで操作する。単純で広く使われる |
| GraphQL | クライアントが必要なデータの形を指定する。過不足のない取得ができる |
| WebSocket | 双方向の持続的な接続。チャット、通知、リアルタイム更新に使う |

データ形式は **JSON** が主流である（かつては XML）。

### クライアントサーバと P2P

通信の形には2つの型がある。

| | クライアントサーバ | P2P（ピアツーピア） |
| --- | --- | --- |
| 役割 | 固定（要求する側／応える側） | 各ノードが両方を担う |
| 管理 | 中央集権的で容易 | 分散していて困難 |
| 単一障害点 | **ある** | ない |
| 拡張 | サーバの増強が必要 | **参加者が増えると資源も増える** |
| 例 | Web、メール | BitTorrent、ブロックチェーン、WebRTC |

**P2P の利点は「参加者が資源を持ち寄る」ことである。**
配信するデータ量が増えても、受け手が同時に配り手になるので、
中央のサーバの負荷が増えない。

2000年代前半、P2P はファイル共有と著作権侵害の文脈で語られ、
社会的な議論の的になった。しかし技術そのものは中立である。
現在の主な応用は次のとおりである。

- **BitTorrent** — 大容量ファイルの配布（Linux の配布イメージ、ゲームの更新）
- **ブロックチェーン** — 中央の管理者なしに台帳を共有する
- **WebRTC** — ブラウザ間の直接通信（ビデオ通話、画面共有）
- **IPFS** — 内容に基づいてデータを指す分散ストレージ

**現実には純粋な P2P は少ない。** 最初に相手を見つける段階
（ピア発見）には中央のサーバを使い、その後の大量データ転送だけを
P2P にする、という混成型が多い。
第9回 9.5 で見た NAT が、任意のノード間の直接接続を難しくしていることも一因である。

### CDN

**CDN** (Content Delivery Network) は、
コンテンツの複製を世界各地に配置し、利用者に**物理的に近い場所**から配信する。

第2回の遅延表を思い出す。東京と米国西海岸の往復は 100ms。
光の速度は変えられないので、**距離そのものを縮める**しかない。

CDN が解決するもの:

- 遅延の短縮（近くから返す）
- 元のサーバの負荷軽減
- 突発的な負荷の吸収
- 大量アクセスによる攻撃の緩和

## まとめ

- UDP は薄く速い。TCP はベストエフォートの上に信頼性を作る。
  信頼性は網ではなく端点が担う（エンド・ツー・エンド原理）
- TCP の輻輳制御は、中央の管理なしにインターネット全体の破綻を防いでいる
- プログラムから見ると通信はソケット＝ファイル記述子であり、
  接続してしまえばファイルと同じ read / write で扱える
- DNS は名前とアドレスを分離し、階層的な委譲によって非中央集権に動く
- HTTP はステートレスで、それゆえにサーバを増やして分散できる。
  HTTP/3 は TCP の限界を避けるため UDP 上の QUIC に移った
- TLS の3つの保証のうち、真正性が土台である
- P2P は参加者が資源を持ち寄る点で優れるが、NAT と発見の問題から
  実際には中央サーバとの混成型が多い
