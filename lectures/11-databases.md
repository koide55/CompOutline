## 11.1 なぜデータベースが要るのか

### ファイルで管理するとどうなるか

第6回でファイルシステムを学んだ。データはファイルに書けばよいのでは、
と思うだろう。学生名簿を CSV ファイルで管理してみる。

```
学籍番号,氏名,学部,科目,担当教員,成績
2S001,山田,工学部,情報基礎,佐藤,85
2S001,山田,工学部,数学,鈴木,90
2S002,田中,理学部,情報基礎,佐藤,78
```

規模が大きくなると、次の問題が現れる。

| 問題 | 内容 |
| --- | --- |
| **冗長性** | 「山田／工学部」が何度も繰り返される |
| **更新の異常** | 学部が変わったとき、全行を漏れなく直せるか |
| **検索の遅さ** | 「情報基礎の受講者」を探すのに全行を読む（第2回の O(n)） |
| **同時アクセス** | 2人が同時に書くと壊れる（第7回の競合状態） |
| **一貫性の破れ** | 書き込み途中で電源が落ちたら中途半端な状態が残る |
| **権限の管理** | ファイル単位でしか制御できない。「成績列だけ隠す」ができない |

**データベース管理システム (DBMS)** は、これらをまとめて解決する。

### DBMS が提供するもの

| 機能 | 内容 |
| --- | --- |
| データモデル | データの構造を宣言的に定義できる |
| 問い合わせ言語 | 「どう探すか」ではなく「何が欲しいか」を書ける |
| インデックス | 検索を O(n) から O(log n) にする |
| トランザクション | 一連の操作をまとめて「全部やるか、全部やらないか」にする |
| 同時実行制御 | 複数の利用者が同時に触っても矛盾しない |
| 障害回復 | 電源断からでも一貫した状態に戻せる |
| アクセス制御 | 表や列の単位で権限を設定できる |

**「どう探すか」を書かなくてよい**という点は特に重要である。
SQL で `WHERE 学部 = '工学部'` と書けば、
DBMS がインデックスを使うか全走査するかを自分で判断する。
データ量が変わってもプログラムを書き直さなくてよい。

これも本講義に繰り返し現れる**抽象化**である。

### CRUD

データに対する基本操作は4つに集約される。

| 操作 | 意味 | SQL |
| --- | --- | --- |
| Create | 作成 | `INSERT` |
| Read | 読み出し | `SELECT` |
| Update | 更新 | `UPDATE` |
| Delete | 削除 | `DELETE` |

頭文字を取って **CRUD** という。
どんな複雑なアプリケーションも、突き詰めればこの4つの組み合わせである。

## 11.2 リレーショナルモデルと正規化

### 用語

1970年に E.F. Codd が提案した**リレーショナルモデル**は、
データを**表**（テーブル）の集まりとして表す。

| 用語 | 別名 | 意味 |
| --- | --- | --- |
| 関係（リレーション） | 表、テーブル | 1つのまとまり |
| 組（タプル） | 行、レコード | 1件のデータ |
| 属性 | 列、カラム、フィールド | 1つの項目 |
| 定義域（ドメイン） | 型 | 属性が取りうる値の範囲 |

**学生**表:

| 学籍番号 | 氏名 | 学部 |
| --- | --- | --- |
| 2S001 | 山田 | 工学部 |
| 2S002 | 田中 | 理学部 |

### キー

| 種類 | 意味 |
| --- | --- |
| **候補キー** | 行を一意に識別できる属性（の組） |
| **主キー** | 候補キーのうち、代表として選んだもの。重複と空値を許さない |
| **外部キー** | 他の表の主キーを参照する属性 |

上の表では `学籍番号` が主キーである。氏名は同姓同名がありうるので使えない。

**外部キーの役割**: 表と表を関係づける。
**成績**表の `学籍番号` が **学生**表を参照していれば、
存在しない学生の成績を登録しようとしても DBMS が拒否する
（**参照整合性**）。

### 正規化

11.1 の CSV の問題を、表の設計で解決するのが**正規化**である。

**正規化していない表**:

| 学籍番号 | 氏名 | 学部 | 科目 | 担当教員 | 成績 |
| --- | --- | --- | --- | --- | --- |
| 2S001 | 山田 | 工学部 | 情報基礎 | 佐藤 | 85 |
| 2S001 | 山田 | 工学部 | 数学 | 鈴木 | 90 |
| 2S002 | 田中 | 理学部 | 情報基礎 | 佐藤 | 78 |

**何が起きるか**（更新時異常）:

| 異常 | 具体例 |
| --- | --- |
| **更新異常** | 山田の学部を変えるとき、複数行を漏れなく直さないと矛盾する |
| **挿入異常** | まだ誰も履修していない科目を登録できない（学生の行がないと入れられない） |
| **削除異常** | 田中の履修を全部消すと、「情報基礎の担当は佐藤」という情報まで消える |

**正規化した設計**:

**学生**（主キー: 学籍番号）

| 学籍番号 | 氏名 | 学部 |
| --- | --- | --- |
| 2S001 | 山田 | 工学部 |
| 2S002 | 田中 | 理学部 |

**科目**（主キー: 科目コード）

| 科目コード | 科目名 | 担当教員 |
| --- | --- | --- |
| C001 | 情報基礎 | 佐藤 |
| C002 | 数学 | 鈴木 |

**履修**（主キー: 学籍番号＋科目コード、両方が外部キー）

| 学籍番号 | 科目コード | 成績 |
| --- | --- | --- |
| 2S001 | C001 | 85 |
| 2S001 | C002 | 90 |
| 2S002 | C001 | 78 |

> **[図 11-1] 正規化前と正規化後**
> 上に正規化前の1枚の大きな表を描き、重複しているセル（山田・工学部が2回、
> 情報基礎・佐藤が2回）を破線で囲んで「冗長」と注記する。
> 下に正規化後の3つの表を並べ、外部キーの参照関係を矢印で結ぶ。
> 「事実は1箇所にだけ書く」という原則を図の下に添える。

**正規化の原則**は一言で言える。

> **1つの事実は、1箇所にだけ書く。**

こうすれば、変更する場所も1箇所になり、矛盾が生じない。

**正規形の段階**:

| 正規形 | 条件 |
| --- | --- |
| 第1正規形 | 1つのセルに1つの値だけ（繰り返しの項目がない） |
| 第2正規形 | 第1正規形＋主キーの一部にだけ依存する属性がない |
| 第3正規形 | 第2正規形＋主キー以外の属性に依存する属性がない |

実務では第3正規形まで行うのが標準である。

**ただし、あえて正規化を崩すこともある**（非正規化）。
正規化すると表が増え、問い合わせのたびに結合が必要になって遅くなる。
読み出しが圧倒的に多い用途では、意図的に冗長を持たせることがある。
**その場合、冗長なデータの整合性を保つ責任がアプリケーション側に移る**
ことを理解した上で判断する。

## 11.3 SQL

**SQL** (Structured Query Language) はリレーショナルデータベースの標準言語である。

**宣言的**であることが特徴である。「何が欲しいか」を書き、
「どう取るか」は DBMS に任せる。

### 射影と選択

**射影**（列を絞る）と**選択**（行を絞る）が基本である。

```sql
-- 工学部の学生の学籍番号と氏名を取り出す
SELECT 学籍番号, 氏名        -- 射影：欲しい列
FROM   学生
WHERE  学部 = '工学部';      -- 選択：欲しい行
```

### 結合

正規化して分けた表を、再びつなげるのが**結合**（JOIN）である。

```sql
-- 誰がどの科目で何点だったか
SELECT 学生.氏名, 科目.科目名, 履修.成績
FROM   履修
       JOIN 学生 ON 履修.学籍番号 = 学生.学籍番号
       JOIN 科目 ON 履修.科目コード = 科目.科目コード;
```

結果:

| 氏名 | 科目名 | 成績 |
| --- | --- | --- |
| 山田 | 情報基礎 | 85 |
| 山田 | 数学 | 90 |
| 田中 | 情報基礎 | 78 |

> **[図 11-2] 内部結合の仕組み**
> 左に「履修」表、右に「学生」表を並べ、
> 履修の各行から、学籍番号が一致する学生の行へ矢印を引く。
> 結果として横に連結された表を下に描く。
> 一致する相手がない行は結果に現れないことを、
> 該当行に×印を付けて示す（内部結合の性質）。

**結合の種類**:

| 種類 | 内容 |
| --- | --- |
| 内部結合 (INNER JOIN) | 両方に一致する行だけ |
| 左外部結合 (LEFT JOIN) | 左の表は全部残し、相手がなければ NULL |
| 交差結合 (CROSS JOIN) | 全組み合わせ（直積）。行数が積になるので注意 |

### 集計

```sql
-- 科目ごとの受講者数と平均点（受講者3人以上のものだけ）
SELECT   科目コード,
         COUNT(*)   AS 受講者数,
         AVG(成績)  AS 平均点
FROM     履修
GROUP BY 科目コード
HAVING   COUNT(*) >= 3
ORDER BY 平均点 DESC;
```

| 句 | 役割 |
| --- | --- |
| `GROUP BY` | 指定した列の値が同じ行をまとめる |
| 集約関数 | `COUNT`, `SUM`, `AVG`, `MAX`, `MIN` |
| `HAVING` | **グループ化した後**の絞り込み |
| `WHERE` | **グループ化する前**の絞り込み |
| `ORDER BY` | 並べ替え（`DESC` で降順） |

**`WHERE` と `HAVING` の違い**は試験でよく問われる。
`WHERE` は個々の行を、`HAVING` は集計結果を絞る。
「成績が60点以上の履修だけを対象に、科目ごとの平均を出し、
そのうち平均が70点以上の科目」なら、`WHERE 成績 >= 60` と
`HAVING AVG(成績) >= 70` の両方を書く。

### 副問い合わせ

問い合わせの中に別の問い合わせを埋め込める。

```sql
-- 全体の平均点より高い成績の履修を取り出す
SELECT *
FROM   履修
WHERE  成績 > (SELECT AVG(成績) FROM 履修);
```

### インデックス

第2回で見た二分探索を思い出す。ソートされていれば O(log n) で探せる。
**インデックス**は、この「探しやすい構造」を列に対して作っておく仕組みである
（実装は多くの場合 B木、あるいはハッシュ）。

```sql
CREATE INDEX idx_gakubu ON 学生(学部);
```

| | インデックスなし | インデックスあり |
| --- | --- | --- |
| 検索 | O(n) 全走査 | O(log n) |
| 挿入・更新・削除 | 速い | **インデックスの更新分だけ遅い** |
| 記憶領域 | 不要 | 追加で必要 |

**インデックスは万能ではない。** 読み出しを速くする代わりに、
書き込みを遅くし、領域を消費する。
検索条件によく使う列にだけ作るのが基本である。

## 11.4 トランザクション

### なぜ必要か

銀行の振込を考える。

```
1. A の口座から 10,000 円引く
2. B の口座に 10,000 円足す
```

**1 の直後に障害が起きたら**、10,000 円が消滅する。
この2つは「両方実行される」か「両方実行されない」かのどちらかでなければならない。

**トランザクション**とは、**まとめて1つの単位として扱われる一連の操作**である。

```sql
BEGIN;
  UPDATE 口座 SET 残高 = 残高 - 10000 WHERE 口座番号 = 'A';
  UPDATE 口座 SET 残高 = 残高 + 10000 WHERE 口座番号 = 'B';
COMMIT;   -- ここで初めて確定する。途中で問題があれば ROLLBACK
```

### ACID 特性

トランザクションが満たすべき性質を、頭文字で **ACID** という。

| 性質 | 内容 | 防ぐ事態 |
| --- | --- | --- |
| **A** 原子性 (Atomicity) | 全部実行されるか、全く実行されないか | 途中で止まって金が消える |
| **C** 一貫性 (Consistency) | 実行の前後で制約が保たれる | 残高が負になる、存在しない学生の成績が入る |
| **I** 独立性 (Isolation) | 同時に実行しても、順番に実行したのと同じ結果になる | 第7回の競合状態 |
| **D** 永続性 (Durability) | 完了したら、障害が起きても失われない | 「完了」と表示された後で消える |

**独立性が第7回とつながる**。複数の利用者が同時に同じデータを更新するのは、
まさにスレッドの競合状態と同じ問題である。
DBMS はロックや多版同時実行制御（MVCC）でこれを解決する。

**永続性の実現**: 変更を実際のデータファイルに書く前に、
**ログに先に書く**（WAL: Write-Ahead Logging）。
障害から復旧するとき、ログを読み直して確定済みの変更を再適用し、
未確定の変更を取り消す。
第6回のファイルシステムのジャーナリングと同じ考え方である。

### 独立性のレベル

完全な独立性は高価である（並行性が下がる）。
そこで段階を選べるようになっている。

| レベル | 許される異常 |
| --- | --- |
| READ UNCOMMITTED | 未確定の値が読める（ダーティリード） |
| READ COMMITTED | 同じ問い合わせを2回して結果が変わる（ノンリピータブルリード） |
| REPEATABLE READ | 集合の要素が増える（ファントムリード） |
| SERIALIZABLE | なし（順番に実行したのと完全に同じ） |

下に行くほど安全だが遅い。**用途に応じて選ぶ**。
残高の計算には SERIALIZABLE、閲覧数の集計には READ COMMITTED、といった判断をする。

## 11.5 大規模化とNoSQL

### 1台では足りなくなったら

データ量とアクセスが増えると、1台のサーバでは処理しきれなくなる。

**スケールアップ**（1台を強力にする）には限界と急激な費用増がある。
そこで**スケールアウト**（台数を増やす）を考えるが、
リレーショナルデータベースは分散が難しい。
ACID を複数台にまたがって保証するのが高価だからである。

| 手法 | 内容 | 課題 |
| --- | --- | --- |
| **レプリケーション** | 同じデータを複製する。読み出しを分散 | 書き込みは分散しない。複製に遅れが生じる |
| **シャーディング** | データを分割して別々のサーバに置く | 複数シャードにまたがる結合とトランザクションが難しい |

> **[図 11-3] レプリケーションとシャーディング**
> 上段にレプリケーション：1台のプライマリから複数のレプリカへ矢印を引き、
> 書き込みはプライマリのみ、読み出しは全レプリカが受けられることを示す。
> 下段にシャーディング：データを「学籍番号 1〜999」「1000〜1999」…と
> 分割し、それぞれ別サーバに置く様子を描く。
> 各方式が「読み書きのどちらを分散できるか」を右に注記する。

### CAP 定理

分散システムには、次の3つを**同時にすべては満たせない**という制約がある。

| | 内容 |
| --- | --- |
| **C** 一貫性 (Consistency) | どのノードに聞いても同じ最新の値が返る |
| **A** 可用性 (Availability) | どのノードも必ず応答を返す |
| **P** 分断耐性 (Partition tolerance) | ネットワークが分断されても動作を続ける |

**ネットワークの分断は必ず起きる**（第9回のとおり、
インターネットは障害を前提としている）。したがって P は諦められない。
実際の選択は **C と A のどちらを取るか**である。

- **C を取る** — 分断中は応答を拒否する。銀行の残高など、
  誤った値を返してはならないもの
- **A を取る** — 分断中も古い値かもしれないが応答する。
  SNS のタイムラインなど、多少古くても止まるより良いもの

**結果整合性** (eventual consistency) は A を取る立場である。
「今すぐは一致しないが、しばらくすれば一致する」ことを保証する。

### NoSQL

リレーショナルモデルにこだわらない DBMS を総称して **NoSQL** という
（"Not Only SQL" と読むことが多い）。

| 種類 | データの形 | 向く用途 |
| --- | --- | --- |
| キーバリュー型 | キー → 値 | キャッシュ、セッション管理 |
| 文書型 | JSON のような入れ子構造 | 構造が一定しないデータ |
| 列指向型 | 列ごとに格納 | 大量データの集計・分析 |
| グラフ型 | ノードと辺 | 人間関係、経路、推薦 |

**列指向が集計に強い理由**: 「全社員の給与の合計」を計算するとき、
行ごとに格納されていると全社員の全項目を読むことになる。
列ごとなら給与の列だけ読めばよい。
第5回の**参照の局所性**が、ストレージのレイアウトの設計として現れている。

**選び方**: 「NoSQL のほうが新しいから優れている」ではない。

- データに明確な構造があり、整合性が重要 → リレーショナル
- 構造が定まらない、あるいは規模が極端に大きい → NoSQL
- 両方 → 併用する（実務ではこれが多い）

近年は、リレーショナルデータベースが JSON 型を持ち、
NoSQL が SQL 風の問い合わせと ACID を持つようになり、
境界は曖昧になっている（NewSQL と呼ばれる分類もある）。

### 大規模データ処理

分析のために大量のデータを一括処理する場面では、
別の道具が使われる。

**MapReduce** の考え方:

1. **Map** — データを分割し、各断片に同じ処理を並列に適用する
2. **Shuffle** — 結果をキーごとにまとめ直す
3. **Reduce** — キーごとに集約する

**なぜこの形なのか**: 第5回のアムダールの法則を思い出す。
並列化できる割合が上限を決める。Map の段階は完全に独立なので
台数に比例して速くなる。
また、どこか1台が壊れてもその断片だけやり直せばよい（耐障害性）。

現在は Apache Spark のような、
中間結果を主記憶に保持してより高速に処理する枠組みが主流である。

**データウェアハウスとデータレイク**:

| --- | --- |

## 演習

**11-1.** CSV ファイルで学生名簿を管理する場合の問題を4つ挙げ、
それぞれ DBMS のどの機能が解決するか対応づけよ。

**11-2.** 次の表は正規化されていない。更新異常・挿入異常・削除異常の
具体例をそれぞれ1つずつ挙げ、正規化した設計を示せ。

| 注文番号 | 顧客名 | 顧客住所 | 商品名 | 単価 | 数量 |
| --- | --- | --- | --- | --- | --- |

**11-3.** 11.2 の3つの表を使って、次の SQL を書け。
(a) 工学部の学生の氏名一覧
(b) 佐藤教員が担当する科目の受講者の氏名と成績
(c) 学生ごとの平均点（氏名とともに）

**11-4.** `WHERE` と `HAVING` の違いを説明し、
両方を使う SQL の例を1つ書け。

**11-5.** インデックスを作ると検索が速くなるが、常に作るべきではない。
理由を2つ挙げよ。

**11-6.** ACID の各特性について、
「その特性がなかったら、銀行の振込で何が起きるか」を1つずつ述べよ。

**11-7.** CAP 定理において、分断耐性 (P) を諦められないのはなぜか。
また、次の各システムは C と A のどちらを優先すべきか、理由とともに答えよ。
(a) 銀行の残高照会 (b) SNS の「いいね」の数 (c) 航空券の座席予約

## まとめ

- ファイルによる管理は冗長性・更新異常・同時アクセス・障害回復で行き詰まる
- リレーショナルモデルはデータを表で表し、キーで表どうしを関係づける
- 正規化の原則は「1つの事実は1箇所にだけ書く」。これが更新異常を防ぐ
- SQL は宣言的で、「何が欲しいか」を書けば取り方は DBMS が決める
- インデックスは検索を速くする代わりに、書き込みを遅くし領域を消費する
- トランザクションは ACID を満たす操作の単位。
  独立性は第7回の競合状態と同じ問題を扱っている
- 分散すると CAP 定理により C と A のどちらかを選ぶことになる
- NoSQL は用途に応じた選択肢であり、優劣ではない
