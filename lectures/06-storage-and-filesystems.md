## 6.1 磁気ディスク

### なぜ今も磁気ディスクを学ぶのか

2026年時点で、個人が使う計算機のストレージはほぼ SSD である。
それでも磁気ディスク（HDD）を学ぶ理由は3つある。

1. **データセンタでは今も現役** — 容量あたりの単価が SSD の数分の1で、
   大量の「あまり読まないデータ」を置く用途では代替がない
2. **「機械の動く記憶装置」の性質が、ソフトウェアの設計に刻まれている** —
   ファイルシステムもデータベースも、HDD の特性を前提に作られてきた
3. **アクセス時間の見積もりが、性能を考える訓練になる**

### 構造

> **[図 6-1] 磁気ディスク装置の構造**
> 上から見た図と横から見た図を並べる。上面図では円盤（プラッタ）を描き、
> 同心円のトラック、それを扇形に区切ったセクタを示す。
> 側面図では複数のプラッタが軸（スピンドル）に重なり、
> それぞれの面にヘッドが向かい、アクセスアームが櫛状に一体で動く様子を描く。
> 全プラッタの同じ半径のトラックの集合が「シリンダ」であることを、
> 縦に貫く筒として示す。

![図 6-1 磁気ディスク装置の構造](../figures/fig-06-01.svg)

| 用語 | 意味 |
| --- | --- |
| プラッタ | 磁性体を塗った円盤。両面に記録する |
| トラック | 1つの面上の同心円 |
| セクタ | トラックを扇形に区切った最小読み書き単位（512B または 4KB） |
| シリンダ | 全プラッタの同じ半径のトラックの集合 |
| ヘッド | 磁気を読み書きする素子。面ごとに1つ |
| アクセスアーム | 全ヘッドを一体で動かす腕 |

**ヘッドが一体で動く**ことが重要である。1つの面のトラック5を読んでいるとき、
他の面もトラック5にいる。だから「同じシリンダ内なら腕を動かさずに読める」。
ファイルを同じシリンダにまとめる、という古典的な最適化はここから来る。

### アクセス時間

データを読むまでにかかる時間は3つの和である。

```
アクセス時間 = シーク時間 + 回転待ち時間 + 転送時間
```

| 要素 | 内容 | 典型値 |
| --- | --- | --- |
| シーク時間 | 腕を目的のシリンダへ動かす | 平均 4〜9 ms |
| 回転待ち時間 | 目的のセクタが来るのを待つ | 平均で半回転分 |
| 転送時間 | データを読み出す | データ量 ÷ 転送速度 |

**回転待ち時間の平均は半回転分**である。目的のセクタが今どこにいるかは
運次第なので、平均すれば半周待つことになる。

7,200 rpm（毎分7,200回転）のディスクなら:

```
1回転 = 60 / 7200 秒 = 8.33 ms
平均回転待ち = 8.33 / 2 = 4.17 ms
```

### 見積もりの例

**問題**: 7,200 rpm、平均シーク時間 8ms、転送速度 200 MB/s のディスクから
4KB を読む。平均アクセス時間はいくらか。

```
シーク時間    = 8 ms
回転待ち      = 4.17 ms
転送時間      = 4 KB ÷ 200 MB/s = 0.02 ms
合計          = 12.19 ms
```

**注目点**: 12.19ms のうち、実際にデータを転送しているのは 0.02ms、
**わずか 0.16%** である。残りは全部「機械が動くのを待っている」時間である。

第2回の遅延表と並べると:

| 操作 | 時間 | 主記憶(80ns)の何倍 |
| --- | ---: | ---: |
| 主記憶参照 | 80 ns | 1 |
| SSD 読み出し | 20 µs | 250 |
| HDD ランダム読み出し | 12 ms | **150,000** |

**この15万倍の差が、ソフトウェア設計のあらゆる場面に影響している。**
データベースがインデックスを持つのも、OS がディスクの内容を主記憶に
キャッシュするのも、この差を埋めるためである。

### 連続読みとランダム読み

上の例は「1箇所を読む」場合だった。**連続した領域**を読むなら話は変わる。
1回シークすれば、あとは回転に任せて次々読める。

| アクセス方式 | 4KB×1000個を読む時間 |
| --- | ---: |
| ランダム（1000箇所） | 12.19 ms × 1000 = **12.2 秒** |
| 連続（4MB を一続きで） | 8 + 4.17 + 20 = **32 ms** |

**約380倍の差**。HDD では「どこを読むか」より「どういう順で読むか」が効く。

SSD ではこの差はずっと小さいが、ゼロではない。
連続アクセスが速いという性質自体は残っている。

### 容量の計算

```
容量 = セクタ長 × 1トラックあたりのセクタ数 × 1面のトラック数 × 面数
```

ただし現代のディスクは**ZBR**（Zoned Bit Recording）を使う。
外周のトラックは内周より長いので、外周により多くのセクタを置く。
そのため「1トラックあたりのセクタ数」は一定でない。

副作用として、**外周のほうが1回転で読める量が多く、転送速度が速い**。
同じディスクでも、使う位置で性能が変わる。

### 容量表示のずれ

第2回で扱った SI接頭辞と2進接頭辞の問題が、ここで実際に現れる。

- 製造者の「1 TB」= 10¹² バイト
- OS が 2⁴⁰ で割って表示 = 0.909 TB

**1TB 買って 0.91TB と表示される。** どちらも間違っていない。

## 6.2 フラッシュメモリと SSD

### 原理

フラッシュメモリは、トランジスタのゲートに電荷を閉じ込めて
情報を保持する。電源を切っても電荷が残るので**不揮発性**である。

DRAM（第5回）との対比:

| | DRAM | フラッシュ |
| --- | --- | --- |
| 電荷の保持先 | コンデンサ | 絶縁層に囲まれたゲート |
| 電源を切ると | 消える | 残る（数年） |
| リフレッシュ | 必要 | 不要 |
| 書き換え回数 | 無制限 | **有限**（数千〜数万回） |

### フラッシュ特有の制約

フラッシュには、他の記憶装置にない厄介な性質が3つある。

**(1) 書き換え回数に上限がある**

同じ領域に何万回も書くと、絶縁層が劣化して電荷を保てなくなる。
記録方式によって寿命が違う。

| 方式 | 1セルのビット数 | 書換え耐性の目安 | 単価 |
| --- | ---: | ---: | --- |
| SLC | 1 | 数万〜10万回 | 高い |
| MLC | 2 | 数千回 | |
| TLC | 3 | 千〜三千回 | |
| QLC | 4 | 数百〜千回 | 安い |

1セルに詰め込むほど安くなるが、電圧を細かく区別する必要があるため
劣化に弱くなる。第2回の「10状態を電圧で区別するのは難しい」という話が、
ここで実際の設計問題として現れている。

**(2) 上書きができない**

書き込みは「1 を 0 にする」方向にしかできない。
0 を 1 に戻すには**消去**が必要で、消去は**ブロック単位**（数 MB）でしか行えない。

読み書きの単位（ページ、数 KB）と消去の単位（ブロック、数 MB）が
食い違うため、「4KB だけ書き換えたい」ときに素朴にやると
数 MB を読み出し→消去→書き戻すことになる（**書き込み増幅**）。

**(3) 摩耗が偏る**

よく書き換える領域だけが先に寿命を迎えると、全体が使えなくなる。

### SSD はこれをどう扱うか

SSD の中には**コントローラ**という小さな計算機が入っていて、
上の制約を隠している。

- **ウェアレベリング** — 書き込み先を全ブロックに散らし、摩耗を均す。
  そのため「論理的な番地」と「物理的な位置」の対応表を常に持ち替える
- **ログ構造の書き込み** — 上書きせず、常に新しい場所に書いて対応表を更新する。
  古いデータは無効印を付けて、あとでまとめて消去する
- **ガベージコレクション** — 無効なページが混ざったブロックから
  有効なページだけを集め直し、ブロックを丸ごと消去して再利用する
- **TRIM** — OS が「このデータはもう不要」と SSD に伝える命令。
  これがないと SSD は削除済みデータを有効と思い込み、
  ガベージコレクションで無駄にコピーし続ける
- **予備領域** — 表示容量より多くのセルを内蔵し、劣化したブロックを置き換える

> **[図 6-2] SSD の論理・物理アドレス変換**
> 上に OS から見た論理ブロック番号の一次元の帯、下に物理的な
> NAND ブロックの格子を描く。両者を結ぶ矢印が交差し、
> 論理的に連続した領域が物理的には散らばっていることを示す。
> 「上書き」の操作で、古い物理ページが無効印になり、
> 新しい物理ページへ矢印が張り替わる様子を2段で描く。

![図 6-2 SSD の論理・物理アドレス変換](../figures/fig-06-02.svg)

**設計思想の共通点**: 第5回の仮想記憶と同じ構図——
「対応表を挟んで、上の層に都合のよい幻を見せる」——がここでも使われている。

### 接続インタフェース

SSD が速くなると、接続経路が足を引っ張るようになった。

| 規格 | 経路 | 帯域の目安 | 備考 |
| --- | --- | --- | --- |
| SATA | AHCI プロトコル | 6 Gbps（実効 550 MB/s） | HDD 時代の設計。SSD には遅すぎる |
| NVMe (PCIe 4.0 x4) | PCI Express | 約 7 GB/s | SSD のために設計されたプロトコル |
| NVMe (PCIe 5.0 x4) | PCI Express | 約 14 GB/s | 2026年時点の主流 |

**NVMe が速い理由は帯域だけではない。** SATA/AHCI は「1つのキューに31個の命令」
しか扱えず、機械的に動くヘッドが1つしかない HDD には十分だった。
NVMe は「6万5千個のキューに、各6万5千個の命令」を扱える。
**内部で数千の処理を並行できる SSD の性質に合わせた設計**である。

装置が変わればプロトコルも変えるべき、という教訓がここにある。

### 光学メディアと磁気テープ

かつて主役だった記憶媒体の現状にも触れておく。

- **CD/DVD/Blu-ray** — 個人用途からはほぼ退場した。
  原理（レーザでピットを読む、色素を分解する、結晶構造を変える）は
  光学記録の教材として価値があるが、実務で扱う場面は少ない
- **磁気テープ** — **むしろ現役**である。LTO 規格は世代を重ね、
  1巻で数十 TB を記録する。容量単価が最も安く、電源なしで長期保存でき、
  ネットワークから切り離せる（ランサムウェア対策として重要）。
  大規模なアーカイブとバックアップでは今も第一選択である

「新しい技術が古い技術を置き換える」とは限らない。
**用途ごとに最適な特性が違うので、階層として共存する**。
第5回の記憶階層の考え方が、ここでも効いている。

## 6.3 冗長化：RAID

### なぜ必要か

ストレージは壊れる。特に HDD は機械的に動く部品を含むため、
計算機の構成要素の中でもとりわけ故障しやすい。

さらに、装置を増やすと**全体としての故障率は上がる**。
1台が5年間に故障する確率が 2% だとしても、100台あれば
どれか1台が壊れる確率はきわめて高くなる。

**RAID** (Redundant Arrays of Inexpensive Disks) は、
複数の安価なディスクを組み合わせ、**性能または信頼性、あるいは両方**を
得る技術である。1988年に Patterson らが提案した。

### 基本となる2つの操作

- **ストライピング** — データを複数台に分散して置く。並列に読み書きでき**速い**
- **ミラーリング** — 同じデータを複数台に置く。1台壊れても**残る**

### 主なレベル

> **[図 6-3] RAID 0/1/5/6 のデータ配置**
> 4台のディスクを縦の列として横に並べ、各行にブロック A, B, C… を配置する図を
> レベルごとに4つ描く。RAID 0 は A,B,C,D が4台に分散。
> RAID 1 は A,A / B,B のように対で重複。
> RAID 5 は A1,A2,A3,Ap のようにパリティを含み、
> パリティの位置が行ごとに右下がりにずれる様子を示す。
> RAID 6 は P と Q の2種類のパリティが同様にずれる様子を示す。

![図 6-3 RAID 0/1/5/6 のデータ配置](../figures/fig-06-03.svg)

| レベル | 構成 | 最小台数 | 使える容量 | 耐えられる故障 | 特徴 |
| --- | --- | ---: | --- | ---: | --- |
| RAID 0 | ストライピングのみ | 2 | 100% | **0台** | 速いが冗長性なし |
| RAID 1 | ミラーリング | 2 | 50% | 1台 | 単純・確実。容量効率が悪い |
| RAID 5 | ストライピング＋パリティ分散 | 3 | (n−1)/n | 1台 | 容量効率と冗長性の折衷 |
| RAID 6 | ストライピング＋二重パリティ | 4 | (n−2)/n | 2台 | 大容量ディスク向け |
| RAID 10 | RAID 1 を RAID 0 で束ねる | 4 | 50% | 構成による | 高性能・高信頼。容量効率が悪い |

RAID 2（ビット単位＋ECC）、RAID 3（ビット単位＋専用パリティ）、
RAID 4（ブロック単位＋専用パリティ）は、現在ほとんど使われない。
RAID 4 はパリティディスクに書き込みが集中してボトルネックになるため、
パリティを分散した RAID 5 に置き換えられた。

### パリティの仕組み

RAID 5 のパリティは**排他的論理和 (XOR)** で作る。

3台のデータが A, B, C なら、パリティ P = A ⊕ B ⊕ C を4台目に置く。

B が壊れたら、残りから復元できる。

```
A ⊕ P ⊕ C = A ⊕ (A ⊕ B ⊕ C) ⊕ C = B
```

XOR は同じ値を2回適用すると打ち消し合う（A ⊕ A = 0）ので、
こうして元のデータが戻る。**第3回で作った XOR ゲートが、
ここで信頼性の道具になっている。**

### RAID 5 の書き込みの重さ

1ブロックを書き換えるだけでも、パリティを更新しなければならない。

```
1. 古いデータを読む
2. 古いパリティを読む
3. 新しいパリティを計算する（新パリティ = 古データ ⊕ 新データ ⊕ 古パリティ）
4. 新しいデータを書く
5. 新しいパリティを書く
```

**読み2回＋書き2回**。これを**書き込みペナルティ**という。
書き込みが多い用途では RAID 10 が選ばれることが多いのは、この重さのためである。

### RAID で守れないもの

**RAID はバックアップではない。** 守れるのは「ディスクの物理的故障」だけである。

| 脅威 | RAID で守れるか |
| --- | --- |
| ディスクの故障 | ○ |
| 誤ってファイルを削除した | **×**（全台から消える） |
| ランサムウェアで暗号化された | **×** |
| 火災・水害で装置ごと失われた | **×** |
| RAID コントローラ自体の故障 | **×** |

さらに現代的な問題として、**再構築中の二次故障**がある。
大容量ディスク（20TB 級）の RAID 5 では、1台故障して交換した後の
再構築に丸1日以上かかる。その間に残りのディスクに全域アクセスの負荷がかかり、
**2台目が壊れる確率が無視できない**。これが RAID 6 や
分散ストレージが求められる理由である。

## 6.4 ファイルシステムと分散ストレージ

### ファイルシステムが提供する抽象化

ストレージは物理的には「番号のついたブロックの列」でしかない。
そこに次の幻を作るのが**ファイルシステム**である。

- **名前でアクセスできる** — ブロック番号ではなく `/home/user/report.txt`
- **可変長で扱える** — ブロック境界を意識しない
- **階層構造がある** — ディレクトリで整理できる
- **メタデータがある** — 所有者、権限、更新日時
- **同時アクセスを調停する** — 複数プロセスからの読み書き

第5回の仮想記憶、6.2 の SSD の対応表と同じく、
**対応表を挟んで上の層に都合のよい抽象を見せる**構図である。

### 主な構成要素

| 要素 | 役割 |
| --- | --- |
| ブロック | 割り当ての最小単位（4KB など） |
| inode（またはそれに相当するもの） | 1ファイルのメタデータと、データブロックの位置 |
| ディレクトリ | 名前と inode の対応表。実体は特殊なファイル |
| 空き領域管理 | どのブロックが未使用かの記録 |
| ジャーナル | 書き込み途中の電源断に備えた記録 |

**ジャーナリング**は重要である。「ディレクトリの更新は済んだが、
データの書き込み前に電源が落ちた」という中途半端な状態を防ぐため、
これから行う変更を先に記録してから実行する。
第11回のデータベースのトランザクションと同じ発想である。

主なファイルシステム: ext4, XFS (Linux), APFS (macOS), NTFS/ReFS (Windows),
ZFS, Btrfs（チェックサムとスナップショットを持つ）。

### 断片化

ファイルを作ったり消したりするうちに、空き領域が細切れになり、
1つのファイルが飛び飛びのブロックに置かれるようになる。
これが**断片化**である。

HDD では断片化が深刻だった。飛び飛びの領域を読むたびにシークが起きるためで、
「デフラグ」という作業が必要だった。
SSD ではシークが無いので影響は小さく、
むしろデフラグは無駄な書き込みを増やして寿命を縮めるため**行わない**。

**装置の特性が変わると、正しい運用も変わる**という例である。

### 分散ストレージ

1台の計算機に収まらない規模になると、話は変わる。

| | RAID | 分散ストレージ |
| --- | --- | --- |
| 単位 | 1台の中の複数ディスク | ネットワーク上の複数サーバ |
| 冗長化の対象 | ディスクの故障 | サーバ・ラック・データセンタの故障 |
| 拡張 | 筐体の限界まで | サーバを足せば伸びる |
| 例 | ハードウェア RAID | Ceph, HDFS, S3 などのオブジェクトストレージ |

冗長化の方式は2つある。

- **レプリケーション** — 同じデータを3箇所に置く。単純で復旧が速いが、容量効率は 33%
- **イレイジャーコーディング** — RAID 6 のパリティを一般化したもの。
  データを k 個の断片に分け、m 個の冗長断片を作る。
  k+m 個のうち任意の k 個があれば復元できる。
  たとえば k=6, m=3 なら容量効率 67% で 3台の故障に耐える

**配置の工夫**: 断片を「別のラック、別の電源系統、別のデータセンタ」に散らす。
ラックの電源が落ちても、データセンタが停止しても、データが残るようにする。

### オブジェクトストレージ

分散ストレージでは、ファイルシステムの階層構造ではなく、
**キーと値の対応**（オブジェクトストレージ）が主流である。

- ディレクトリ階層がないので、名前解決を分散させやすい
- 部分更新をせず、丸ごと置き換える（PUT）ので整合性が単純になる
- HTTP でアクセスする（第10回の内容とつながる）

## まとめ

- HDD のアクセス時間はシーク＋回転待ちが支配的で、転送は1%にも満たない。
  ランダムアクセスと連続アクセスで数百倍の差が出る
- フラッシュは不揮発だが、書換え回数の上限・ブロック単位の消去・摩耗の偏りという
  制約がある。SSD のコントローラが対応表を挟んでこれを隠している
- NVMe は SSD の並行性に合わせて設計されたプロトコルで、帯域だけでなく
  キューの構造が SATA と根本的に違う
- 磁気テープは容量単価と長期保存、オフライン性で今も現役である
- RAID はディスクの物理故障に備える技術で、バックアップの代わりにはならない
- ファイルシステムはブロックの列に名前・階層・メタデータの抽象を与える
- 大規模になると RAID から分散ストレージへ移り、
  冗長化の対象がディスクからデータセンタへ広がる
