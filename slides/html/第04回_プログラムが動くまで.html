4.1　機械語

アセンブリ言語と機械語の対応

CPU が実行できるのは ISA が定める命令だけで、主記憶の中では単なる2進数である。

アセンブリ言語と機械語はほぼ1対1に対応する。変換するプログラムをアセンブラという。

人間が16進数を直接書くこともできる（1950年代はそうしていた）。しかし数値を見ても何の命令か分からず、
命令を1つ挿入すると以降のジャンプ先の番地がすべてずれる。

4.1　機械語

それでもアセンブリでは足りない

CPU ごとに違う
x86-64 で書いたコードは Arm では動かない
抽象度が低い
「配列を順に足す」を書くのに10行以上かかる
思考の単位と合わない
人は「レジスタ」ではなく「合計」「顧客リスト」で考える
それでも「読める」ことには価値がある
最適化の結果を確認する、脆弱性を解析する、デバッガでクラッシュ箇所を追う —— いずれも機械語の層に降りる場面である。

書く場面は限られる（OS の起動処理、割り込みハンドラ、暗号処理の定数時間実装など）。

4.2　処理系

処理系の3方式

高級言語を実行するには、機械語に翻訳するか、解釈しながら実行するかのどちらかが要る。

4.2　処理系

コンパイラとインタプリタ

コンパイラ方式　C, C++, Rust, Go
  • 実行時に翻訳の手間がない
  • プログラム全体を見て最適化できる
  • 実行前に型の誤りを検出できる

欠点：実行までに時間がかかる。CPU・OS ごとに別の実行ファイルが要る。

インタプリタ方式　シェルスクリプト等
  • すぐ実行できる
  • 書いて試すサイクルが速い
  • どの環境でも同じソースが動く

欠点：実行のたびに解釈するので遅い。誤りが実行時まで見つからない。

中間に仮想機械方式がある。中間表現（バイトコード）に翻訳し、各環境の VM が解釈する（Java, C#, Python）。

9
4.2　処理系

JIT コンパイル

VM 方式でも、バイトコードの解釈は機械語の直接実行より遅い。そこで実行しながら、よく通る箇所だけを機械語に翻訳する。

実行時にしか分からない事実を使って最適化できる
  • このループで x は常に整数だった 整数専用のコードを出す
  • この分岐はほぼ常に真だった 真の側を速い経路にする
  • 仮定が外れたら 解釈実行に戻せばよい

プログラムの実行時間の大半はごく一部のコードに集中する。全体を最適化するより、熱い箇所だけを本気で最適化するほうが効率がよい。
採用例：JVM (HotSpot)、JavaScript エンジン (V8)、.NET、PyPy。

「コンパイラ言語 vs インタプリタ言語」という分類は、現代ではあまり意味をなさない。

4.3　ビルド

コンパイルの中身

コンパイル段階が本体で、内部はさらに数段階に分かれる。

  • 字句解析 — 文字列をトークンに分割する
  • int, sum, =, 0, ; といった単位に切る
  • 構文解析 — トークン列から構文木を作る。文法に合わなければ構文エラー
  • 意味解析 — 型が合っているか、変数が宣言済みかを検査
  • 中間表現の生成と最適化 — 不要な計算を除去、ループを変形、定数を畳み込む
  • x = 3 * 4 はコンパイル時に x = 12 になる（定数畳み込み）
  • ループ内で値の変わらない計算はループの外に出される
  • コード生成 — 対象 CPU のアセンブリを出力。レジスタの割り当てもここ

最適化はプログラムの意味を変えてはならない。C の「未定義動作」ではこの制約が外れ、事故の原因になる。

13
4.3　ビルド

リンク：静的と動的

静的リンク

ライブラリの中身を実行ファイルに取り込む。

単体で動くが大きくなる。ライブラリの更新には再リンクが要る。

動的リンク

実行時にライブラリを読み込む。

実行ファイルは小さく、ライブラリを更新すれば全プログラムに反映される。ただし依存するライブラリが無いと動かない。

Linux の .so、Windows の .dll、macOS の .dylib。「DLL が見つかりません」は動的リンクの帰結である。

4.3　ビルド

プロセスのメモリ配置

変数がどこに置かれるかを意識すると、バグの性質が見えてくる。

スタックの変数は関数を抜けると消える／ヒープは明示的に解放しないと残る（メモリリーク）／
テキスト領域は書込み禁止。第12回のバッファオーバフロー攻撃は、この配置を知らないと成立が理解できない。

4つの軸で位置づける

実行の仕方
コンパイル／インタプリタ／仮想機械／JIT
型の扱い

4.5　バージョン管理

バージョン管理が解決すること

ソースコードは1回書いて終わりではない。直し、戻し、複数人で同時に触る。

履歴を残す
「なぜこう書いたか」が後から追える
任意の時点に戻せる
壊したときに引き返せる
変更を統合できる
同じファイルを同時に触っても失われない
分岐して試せる
本流を壊さずに実験できる
「いつ壊れたか」は二分探索で特定できる
1か月前は動いていたが、いま動かない。その間にコミットが100個ある。真ん中で試し、動けば後半、動かなければ前半に絞る —— 7回で1個になる（第2回の二分探索。git bisect が自動化する）。

コミットは「中途半端な状態を記録しない」単位である。第11回のトランザクションと同じ考え方。

21
4.5　テスト

テストは、バグが無いことを証明しない

単体・結合・回帰の3種類がある。自動化がいちばん効くのは回帰テストである —— 人間は一度直した箇所を二度と確かめないが、機械は毎回確かめる。

テストはバグの存在を示せるが、不在は示せない
  • テストが通った バグが見つからなかった
  • バグが無い 別の主張

第1回のライスの定理 —— プログラムの振る舞いに関する自明でない性質は、すべて決定不能である。
テストは有限個の入力で試すだけなので、試していない入力については何も言えない。

型検査とテストは競合しない。型は全入力について「ある種の誤りが無いこと」を保証し、テストは「ある入力で正しく動くこと」を示す。

22
4.5　テスト

第1回の3つの迂回策が、そのまま道具になる

決定不能性は技術の未熟さではない。だから「迂回する」ことが開発の道具立てそのものになる。

第1回の迂回策対応する道具何をしているか
近似するテスト、静的解析有限個の入力で試す。危ない箇所を過剰に報告する
対象を狭める型システム（4.4）決定可能な性質だけを、機械が全入力について保証する
人間を入れるコードレビュー機械に判定できないことを人が見る
継続的インテグレーション（CI）—— コミットごとに自動でビルドしてテストを走らせる

狙いは1つ。壊れたことを早く知る。壊れてから気づくまでが長いほど原因の候補が増える。
コミットごとに確かめれば候補は常に1個なので、二分探索する必要すらなくなる。

まとめ

  • 機械語とアセンブリほぼ1対1に対応する。ラベルを番地に直すのがアセンブラの仕事
  • 処理系コンパイラ・インタプリタ・仮想機械・JIT。現代の言語は複数を組み合わせている
  • ビルド前処理→コンパイル→アセンブル→リンク→ロード。リンクで未解決の番地が埋まる
  • メモリ配置テキスト・データ・ヒープ・スタック。この配置がバグの性質も攻撃の成立も決めている
  • 言語の選択生態系・性能要件・保守性で決まる。「良い言語」という問いは立たない
  • バージョン管理とテストテストはバグの不在を示せない。第1回の迂回策3つが、テスト・型・レビューに対応する
