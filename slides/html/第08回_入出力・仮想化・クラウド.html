入出力の基本問題

CPU から見れば、周辺装置は止まっている

8.1　入出力

速度差という現実

第2・5・6回で見た遅延を、もう一度並べる。

対象時間CPU の1サイクルを1秒とすると
CPU の1サイクル0.3 ns1秒
主記憶80 ns4分
NVMe SSD20 µs18時間
HDD（ランダム）12 ms1年3ヶ月
ネットワーク（国内往復）20 ms2年
キーボードの1打鍵100 ms 以上10年以上
もし CPU が「装置が終わるまで待つ」設計だったら、時間の99.99%以上が待機になる

入出力の仕組みの全体が、この待ち時間をどう使うかという問題への答えである。

8.1　入出力

ポーリングと割り込み

ポーリング
while (状態 != 準備完了) {
    ;  /* 聞き続ける */
}
データを読む

単純で、準備完了を即座に検知できる。しかし待っている間、CPU が丸ごと無駄になる。

待ち時間が短いと分かっている場合は有効

割り込み

CPU が装置に聞きに行くのではなく、装置が終わったときに CPU に知らせる。

CPU は入出力を依頼したらそのプロセスを待機状態にして、別のプロセスを実行する。装置から信号が来たら、そこで初めて対応する。

第7回の多重プログラミングは、割り込みがあって初めて成立する

高速な NVMe や10Gbps を超えるネットワークでは、割り込みのオーバヘッドのほうが大きく、あえてポーリングする設計もある。

8.1　入出力

割り込み処理の流れ

状態を退避し、ハンドラを実行し、復元して再開する。割り込まれた側は中断に気づかない。

8.1　入出力

割り込みの種類

種類きっかけ例
外部割り込み周辺装置から入出力完了、キー入力、ネットワーク受信
タイマ割り込み時計から定期的にスケジューラが制御を取り戻す（第7回）
内部割り込み（例外）実行中の命令自体ゼロ除算、ページフォルト、不正な命令
ソフトウェア割り込み命令で意図的にシステムコール（第7回）
タイマ割り込みがなければ、暴走したプログラムから OS が制御を取り戻せない

ページフォルトも割り込みである。第5回で見た「必要なページが主記憶にない」状態は内部割り込みとして
OS に通知され、OS がページを読み込んでから、中断した命令をやり直す。

8.1　入出力

DMA：転送そのものを任せる

割り込みで待ち時間は解決した。しかしデータの転送そのものを CPU が行っていては、手が空いても転送で塞がる。

デバイスドライバと入出力装置

契約を決めて、中身を差し替え可能にする

8.2　装置

デバイスドライバという層

新しい装置が出ても、アプリケーションを書き直さずに済む
  • アプリケーション read() システムコール
  • カーネル 統一されたインタフェース
  • デバイスドライバ 装置固有の作法
  • ハードウェア 実際の装置

第3回の ISA、第4回のリンク、第6回のファイルシステムと同じ構図である。
ただしドライバはカーネル空間で動くため、バグがあるとシステム全体が落ちる。Windows のブルースクリーンの多くはドライバに起因する。

8.2　装置

入出力装置の原理は、いくつかの型しかない

入力：物理量を電気信号にする
  • キーボード — 格子状の配線を走査し、押された交点を検出
  • 光学式マウス — 表面を高速で撮像し、直前の画像とのずれから移動量を算出
  • 静電容量式タッチパネル — 指が近づくと変化する電極間の容量を検出
  • イメージセンサ — 光電効果で光を電荷に変え、数値化
出力：電気信号を物理量にする
  • 液晶 — 電圧で液晶分子の向きを変え、偏光板を通る光量を制御
  • 有機EL — 素子自体が発光。バックライト不要で黒を完全に消せる
  • レーザープリンタ — 感光体に静電潜像を描き、トナーを転写・定着
  • インクジェット — 熱またはピエゾ素子でインクの液滴を飛ばす

代表例を押さえておけば、新しい装置も理解できる。

8.2　装置

キーマトリクス：時間で空間を節約する

104個のキーに1本ずつ線を引けば104本要るが、格子にすれば21本で済む。

走査という時間の使い方で、空間（配線）を節約している。
計算機科学に繰り返し現れる、時間と空間のトレードオフである。

8.3　仮想化

抽象化をもう一段上げる

ここまでで OS は次の抽象を提供してきた。次の一手は「計算機そのもの」を抽象化することである。

物理メモリ
仮想アドレス空間（第5回）
ブロックの列
ファイル（第6回）
1個の CPU
複数のプロセス（第7回）
個々の装置
統一されたインタフェース（8.2）
仮想化とは
1台の物理計算機の上に複数の「仮想的な計算機」を作る技術。各 VM は独立した OS を持ち、自分専用のハードウェアがあると信じている。これを実現するのがハイパーバイザである。

得られるもの：集約／分離／可搬性（ライブマイグレーション）／柔軟性。この4つがそのままクラウドの技術的基礎になる。

16
8.3　仮想化

仮想機械とコンテナ

仮想機械には無駄がある。OS を丸ごと複製していることである。

コンテナはカーネルを1つ共有したまま、プロセスから見える世界だけを分離する。

17
8.3　仮想化

どちらを選ぶか

仮想機械コンテナ
分離するものハードウェアプロセスの名前空間と資源
カーネルゲストごとに1つホストのものを共有
起動時間数十秒1秒未満
メモリ消費GB 単位MB 単位
分離の強度強い中程度（カーネルの脆弱性は共有される）
異なる OS動かせる動かせない

強い分離が要るとき（異なる顧客のワークロード、信頼できないコードの実行）は仮想機械、
自分たちのアプリを効率よく多数動かすときはコンテナ。クラウドでは「VM の中でコンテナ」が一般的である。

コンテナが数千になると人手で管理できない。これを自動化するのが Kubernetes などのオーケストレータである。

8.4

クラウドコンピューティング

本質は技術ではなく、失敗のコストが下がったこと

8.4　クラウド

何が変わったのか

自前で持つ（オンプレミス）クラウド
調達見積り・発注・搬入・設置に数週間〜数ヶ月数分
費用の性質設備投資（先に大きく払う）経費（使った分だけ）
容量の決め方ピークに合わせて買う需要に応じて増減
失敗のコスト買った機材が無駄になる消せば止まる
もっとも重要な変化は、失敗のコストが下がったこと

履修登録システムは年に数日だけ極端な負荷がかかり、残りの360日は遊んでいる。
自前ならピークに合わせた設備が1年中遊ぶ。「試してみて、駄目ならやめる」が数千円でできるようになった。

8.4　クラウド

サービスモデルと責任分界

事業者は施設・機材・ハイパーバイザを、利用者はアクセス権限・データの暗号化・アカウント管理を担う。
現実の情報漏洩の多くは、事業者側ではなく利用者側の設定ミスによる。

21
8.4　クラウド

暗黒面

利点だけを見るのは危険である。

ベンダロックイン
固有のサービスに依存すると、移行が事実上不可能になる
障害の巻き添え
事業者の障害で、無関係な多数のサービスが同時に止まる
費用の逆転と予測困難
使用量が安定して大きいと自前のほうが安い。設定ミスや攻撃で請求が跳ね上がる
データの所在
法域をまたぐ保管が、GDPR や個人情報保護法に抵触しうる
可視性の低下
内部で何が起きているか分からず、問題の切り分けが難しい
サービス終了
事業者の都合で機能が廃止される

大規模な事業者ほど障害の影響範囲が広い。効率のための集中が、社会全体の脆弱性になっている。

まとめ

  • 速度差周辺装置は CPU から見れば止まっている。入出力の仕組みは、この待ち時間をどう使うかへの答え
  • 割り込み装置側から知らせることで待ち時間を他の処理に使える。タイマ割り込みが OS の制御権を保証する
  • DMA転送そのものを専用コントローラに任せ、CPU を解放する
  • ドライバ装置ごとの差を吸収し、統一されたインタフェースを保つ
  • 仮想化とコンテナ仮想化は計算機そのものを、コンテナはカーネルを共有してより軽量に分離する
  • クラウド本質は調達の速さと失敗コストの低下。ただし責任は共有であり、集中リスクを伴う
