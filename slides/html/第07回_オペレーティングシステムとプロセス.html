7.1

OS は何をしているか

資源を配り、面倒な現実を隠す

7.1　OS の役割

OS の仕事は2つに尽きる

(1) 資源管理 — 有限な資源を複数のプログラムに配分する。(2) 抽象化 — 面倒な現実を扱いやすい形に見せる。

現実OS が見せる抽象
ブロックの列としてのストレージファイルとディレクトリ（第6回）
物理的に断片化した主記憶連続した仮想アドレス空間（第5回）
機種ごとに違う周辺装置統一されたインタフェース
1個の CPUプログラムごとに専用の CPU があるかのような幻
この2つは表裏一体である

「専用の CPU があるように見せる」ためには CPU 時間を細かく切り替えて配分しなければならないし、
「ファイル」という抽象を維持するには空きブロックを管理しなければならない。

5
7.1　OS の役割

なぜ OS が必要になったか

初期の計算機に OS はなかった。問題は、計算機が高価だったことである。

1
逐次処理
1つずつ実行する
2
バッチ処理
仕事をまとめて自動で流す
3
多重プログラミング
1つが入出力待ちの間に別のを走らせる
4
時分割（TSS）
細かく切り替えて、全員が同時に使っている感覚を作る
5
現在
ネットワーク越しに大量の利用者が同時に使う

転換点は「入出力待ち」だった。HDD のアクセスは主記憶の15万倍遅い（第6回）。
この待ち時間に別のプログラムを走らせれば、CPU の利用率は劇的に上がる。

今は「高価な資源を遊ばせない」ためではなく「利用者が同時に多くのことをしたい」ためにある。

6
7.1　OS の役割

特権モードとシステムコール

アプリケーションが OS を無視してハードウェアを触れるなら、管理は成立しない。そこで CPU に2つの動作モードを用意する。

入口が1つしかなく、そこで必ず検査される。この構造がシステム全体の安全性を支えている。

7
7.1　OS の役割

システムコールの手順とコスト

呼び出しから復帰まで
1. 引数を用意し、専用の命令を実行
   （x86-64 なら syscall 命令）
2. 特権モードに切り替わり、
   カーネルの入口へジャンプ
3. カーネルが引数を検査する
4. カーネルが実際の処理を行う
5. 非特権モードに戻り、続きへ返る
システムコールは高価である

モード切替、レジスタの退避と復元、キャッシュへの影響があるため、通常の関数呼び出しの数十〜数百倍のコストがかかる。

だからライブラリは書き込みをバッファに溜め、まとめて1回の write にする。

普段書く print("hello") も、たどれば write システムコールに行き着く。

プロセス

実行中のプログラムに、独立した世界を与える

7.2　プロセス

プロセスの状態遷移

プロセスとは実行中のプログラムである。プログラム（ディスク上の実行ファイル）とは別物で、1つのプログラムから複数のプロセスを作れる。

コア数を超えるプロセスは同時に「実行中」になれない。残りは Ready の列に並ぶ。

10
7.2　プロセス

コンテキストスイッチのコスト

切り替えでやること
  • 現在のプロセスのレジスタを PCB に退避
  • 次のプロセスの PCB からレジスタを復元
  • ページテーブルを切り替える
  • 次のプロセスの PC から実行を再開
本当に効くのは間接的な影響

直接の切替時間は数マイクロ秒。しかし切り替えると、キャッシュの中身が前のプロセスのもののままになる。新しいプロセスは最初ほぼ全部ミスする（キャッシュ汚染）。

TLB も同様に効かなくなる。

だから切り替えは「頻繁すぎず、粗すぎず」に調整する必要がある。

11
7.2　プロセス

プロセスの生成：fork と execve

Unix系では、プロセスは2段階で作る。シェルがコマンドを実行するとき、fork して子を作り、子が execve でそのコマンドに化ける。

fork は全メモリをコピーしない。copy-on-write を使う
  • 親子で同じ物理ページを共有 書込み禁止にしておく
  • どちらかが書き込んだ瞬間 そのページだけ複製する
  • fork の直後に execve するなら どうせ捨てるメモリをコピーせずに済む

第5回の仮想記憶が、こういう芸当を可能にしている。

12
7.2　プロセス

ファイル記述子とパイプ

Unix系のプロセスは、起動すると 0（標準入力）1（標準出力）2（標準エラー出力）を開いた状態で始まる。

プログラムは「画面に書く」のではなく「1番に書く」だけ。1番がどこにつながっているかは知らない。

13
7.2　プロセス

ls -l | wc で起きていること

ls と wc は互いの存在をまったく知らない。それでも ls の出力が wc の入力になる。

① pipe
一方向の通信路を作る。読み口と書き口、2つの記述子が返る
② fork
子プロセスを2つ作る
③ dup
1つ目の子でパイプの書き口を1番に、2つ目の子で読み口を0番に付け替える
④ execve
それぞれ ls と wc に化ける
ここで効いている設計
入出力を番号で抽象化したので相手が何でも read/write で済む。fork と execve を分けたので、その間に記述子を付け替える隙間が生まれる。

| という1文字の裏側に、システムコールが4種類動いている。

スレッドとスケジューリング

同じ記憶を共有する、軽い実行の流れ

7.3　スレッド

プロセスとスレッドのメモリ配置

スタックだけが別。ヒープ・データ・テキストは共有する。

生成も切替も軽い（ページテーブルの切替が要らない）。ただし一方が異常終了するとプロセスごと落ちる。
そして「そのまま共有できる」ことは、利点であり最大の危険でもある。

16
7.3　スケジューリング

何を最適化するかは用途で変わる

Ready 状態のものから次に実行するものを選ぶのがスケジューラである。

指標意味重視する用途
スループット単位時間あたりの完了数バッチ処理
応答時間要求してから反応するまで対話的な用途
公平性特定のものが飢えない多人数で共有するシステム
締切の遵守決められた時刻までに終わる制御システム
全部を同時に最適化することはできない

応答時間を良くするには細かく切り替える必要があるが、切替のたびにコストがかかりスループットは落ちる。
横取り（プリエンプション）ができないと、1つのプログラムの暴走でシステム全体が固まる。

17
7.3　スケジューリング

優先度逆転

低優先度の L がロックを取る → 高優先度の H が同じ資源を待つ → 中優先度の M が L を横取りする → L が動かずロックが解放されない。

結果
高優先度の H が、中優先度の M に負ける
実例
1997年、火星探査機マーズ・パスファインダーがこの問題で再起動を繰り返した
対策：優先度継承
ロックを持っている間だけ、待たせている相手の優先度を一時的に引き継ぐ

現代の汎用 OS はすべて横取り式で、タイマ割り込み（第8回）で定期的に制御を取り戻している。

7.4　競合状態

競合状態

count = count + 1 は1行に見えるが、機械語では LOAD / ADD / STORE の3命令になる。

2回加算したのに 7 にならず 6 になった。更新が1つ失われた。

ほとんどの場合は正しく動く。壊れるのは特定のタイミングのときだけ。
テストで再現せず、負荷が高いときや本番環境でだけ起き、デバッガを付けると再現しなくなる。

20
7.4　排他制御

排他制御の手段

複数のスレッドが同時に触ってはいけない部分をクリティカルセクションといい、同時に1つしか実行できないようにする。

ミューテックス
ロックを取った1つだけが進める。他は待つ
セマフォ
同時に入れる数を n 個に制限する
条件変数
ある条件が成立するまで待ち、成立したら起こしてもらう
アトミック操作
ハードウェアが「読んで書く」を分割不能に実行する

compare-and-swap のようなアトミック命令はロックそのものの実装に使われる。第3回の ISA が並行処理の土台にもなっている。

21
7.4　デッドロック

デッドロック

A は X を持ち Y を待つ。B は Y を持ち X を待つ。両方とも永久に進まない。

コフマンの4条件（相互排除／保持と待機／横取り不可／循環待ち）のどれか1つを崩せば起きない。

実務でもっともよく使われるのは循環待ちを崩す方法 —— 資源に順序を決め、必ずその順に取得する。
規律を守るだけで済むので、実装が単純である。

22
7.4　並行処理

より安全な抽象へ

共有メモリとロックは正しく書くのが難しい。そのため別の抽象が使われるようになっている。

手法考え方例
メッセージパッシングメモリを共有せず、値を送り合うGo のチャネル、Erlang
イミュータブルなデータ書き換えないので競合しない関数型言語の流儀
async / await待ち時間を明示し、切替点を限定するJavaScript, Python, Rust
所有権同時に書ける参照が1つだけとコンパイラが保証Rust

Go の標語「メモリを共有して通信するな、通信によってメモリを共有せよ」は、この転換をよく表している。

まとめ

  • OS の役割資源管理と抽象化の2つ。両者は表裏一体である
  • 特権モード入口を1つに絞って必ず検査する構造が、システム全体の安全性を支える
  • プロセス独立したアドレス空間を持ち、互いに干渉できない
  • 記述子とパイプfork と execve が分かれているから、その間に記述子を付け替えられる
  • スケジューリングスループット・応答時間・公平性は同時に最適化できない
  • 競合とデッドロック競合状態はテストをすり抜ける。デッドロックは資源の取得順序を統一して防ぐ
