# 理解度確認（AI対話）

各回の終わりに、学生が AI と対話して理解度を確かめる。
対話ログと所見を記録し、**教員が成績を判断するための参考資料**とする。

実行基盤は別リポジトリの [cyber-social-implementation-arena](https://github.com/koide55/cyber-social-implementation-arena)。
ここにはシナリオ（何を問うか）と、その検証道具を置く。
シナリオは講義ノートから起こすので、講義と一緒に版を管理するのが自然なため。

## 一線

**AI は点数をつけない。成績は教員が判断する。**

AI がするのは、対話の記録と、教員が短時間で判断するための前処理だけである。
理由は第13回で扱うとおり、LLM の評価には再現性・公平性・説明責任の問題があり、
不利益処分の根拠にはできないため。学生にも明示する。

## 構成

| パス | 内容 |
| --- | --- |
| `lectures/lecNN.py` | 各回の内容（何を問うか） |
| `tools/kit.py` | 共通骨格（どう問うか）。13回ぶんの体裁をここで決める |
| `tools/build.py` | シナリオを書き出す。JSON を直接編集しない |
| `tools/check.py` | シナリオを機械的に検査する |
| `tools/dryrun.py` | 対話ログから所見を作る。学生に配る前の確認用 |
| `tools/install.sh` | シナリオを arena に配置する |
| `scenarios/lecNN.json` | 書き出されたシナリオ（arena の形式） |
| `samples/` | 動作確認用の見本対話 |

内容と体裁を分けてあるので、**体裁の変更は `kit.py` を1箇所直せば全13回に効く。**

## 採点キーの読み替え

arena の `scores` テーブルと `server.py` は **8つのキーを固定**で持つ。
キー名は変えられないので、**意味だけを理解度確認向けに割り当て直した**。
これによりコード改修なしで動く。

| arena のキー | 本講義での意味 | 配点 |
| --- | --- | ---: |
| `technical_accuracy` | 定義の正確さ | 20 |
| `risk_organization` | 限界とトレードオフの理解 | 15 |
| `social_implementation` | 実務への接続 | 10 |
| `plain_language` | 平易な説明 | 10 |
| `cutout_resilience` | 誤った前提の訂正 | 15 |
| `practical_advice` | 自分で例を作る力 | 10 |
| `expertise` | 講義内容の定着 | 15 |
| `trustworthy_attitude` | 誠実さ | 5 |

label は回ごとに差し替えられる（第1回の `risk_organization` は「「計算できない」の理解」）。
配点は arena が総合点を出すために要求する数値であり、**成績ではない**。
教員が見るのは A / B / C と、その根拠となる引用である。

## 設計上の判断と、その根拠

いずれも `gemma4:latest` で実測して決めた。

### 1. 観点ごとに個別に呼ぶ

8観点を1回でまとめて書かせると、判定が甘くなり、字数制限も守られなかった。

```
まとめて1回   16.2秒  最重要観点が B（甘い）  コメントが120字に膨張し文が破綻
観点ごとに8回   9.7秒  同じ観点が C（妥当）    コメントは25〜40字に収まる
```

**個別に呼ぶほうが速い。** 1回あたりの生成量が減るためである。

### 2. 観点によっては、該当する問だけを渡す

全問を渡すと、**目立つ誤答に引きずられる**。
「定義の正確さ」は正しく答えられているのに、別の問での誤りを根拠に B と判定された。
`questions` を指定して範囲を絞ったところ A に直った。

指定がない観点は全問を見る。

### 3. 引用が実在するかを機械で検査する

モデルは、学生が書いていない文を「根拠」として提示することがある。
実測では8観点中1〜2件で起きた。**根拠が捏造されると教員の判断を誤らせる**ので、
学生の発言と照合し、実在しない引用は表示しない。

質問文をそのまま引用してくることもあるため、照合は**学生の発言のみ**と行う。

### 4. A / B / C の判定基準を明示し、誤った前提を教える

第1回だけで調整したものを第12回に当てたところ、**8観点すべてが B に寄り**、
判別できなくなった。2つ足して直した。

- **判定の目安**（A / B / C それぞれの条件）を渡す。これがないと中央に寄る
- **その問に仕込んだ誤った前提を明示する。** 「暗号化されていれば安全」のように
  部分的に正しい記述を含む同意は、汎用の基準だけでは B と判定されてしまった

これで第1回・第12回とも、揺さぶりに同意した回答を C と判定するようになった。

**1つの回で調整したものが他の回で通用するとは限らない。** 展開する前に
別の回で必ず試すこと。

### 5. `temperature=0` と seed 固定

同じ回答に必ず同じ所見が出る。「なぜこの所見か」を後から再現できないと、
成績の参考資料として説明責任を果たせない。
既定の温度では、同じ回答に対して評価が1段階ぶれることを確認している。

### 6. モデルは `gemma4:latest`

8モデルを比較して選んだ。速度・引用の忠実さ・判別力のいずれでも最良だった。
比較の詳細は本文書末尾の「モデル選定」を参照。

## 揺さぶりの問い（各回の問6）

各回の問6には、その回が正そうとしている典型的な誤解を仕込んである。
借り物の答えでは通りにくく、理解度の指標として有効だった。

| 回 | 仕込んだ誤った前提 |
| ---: | --- |
| 1 | 量子コンピュータなら停止問題も解ける |
| 2 | CPU が100倍速くなれば O(n²) も実用的になる |
| 3 | ムーアの法則が終わったので性能はもう上がらない |
| 4 | インタプリタ言語はコンパイラ言語より必ず遅い |
| 5 | コア数を2倍にすれば処理時間は半分になる |
| 6 | RAID があればバックアップは不要 |
| 7 | スレッドは軽いので常にスレッドを使うほうがよい |
| 8 | クラウドを使えばセキュリティは事業者に任せられる |
| 9 | IP アドレスがあれば MAC アドレスは要らない |
| 10 | TCP は UDP より常に優れている |
| 11 | インデックスを全部の列に張れば速くなる |
| 12 | 通信が暗号化されていれば安全 |
| 13 | LLM は大量に学習しているので事実は信頼できる |

## 質問の作り方

**その回固有の内容を問う。** 宿題として出す以上、学生は外部の LLM に
答えさせられる。一般的な LLM が答えにくい問いにしておく必要がある。

第1回では次のようにした。

- 講義で実際に挙げた例（「塩少々」）を前提にした問い
- **誤った前提を含む揺さぶり**（問6「量子コンピュータなら停止問題も解けますよね」）
- 自分の理解の変化を問う（問10）

問6は演習1-3 に対応する。誤った前提に流されるかどうかは、
借り物の答えでは通りにくく、理解度の指標として有効だった。

## 使い方

```bash
python3 assessment/tools/build.py                            # 全13回を書き出す
python3 assessment/tools/check.py                            # 機械的に検査する
python3 assessment/tools/dryrun.py assessment/samples/lec01-mid.json   # 所見を確認
assessment/tools/install.sh                                  # arena に配置
```

`dryrun.py` は `ollama` が動いていることが前提。モデルは環境変数で変えられる。

```bash
ASSESS_MODEL=gemma3:12b python3 assessment/tools/dryrun.py assessment/samples/lec01-mid.json
```

## arena 側に入れたもの

`dryrun.py` で確かめた作り方は、arena の `feature/lecture-assessment` に移した。
学生が答え終わると、採点のあとに所見が自動で作られる。

- `sessions` に学籍番号・氏名の欄
- `observations` テーブルと生成（観点ごとに1回、`temperature=0`、引用の実在検査）
- 教員用の一覧画面（`/teacher`）と、行を開くと出る所見・対話の全文
- 要確認フラグ（短い、長い、講義固有語が少ない、評価が割れている、
  引用の裏取りができない、採点が代替値）
- 締切前の順番待ち（`InferenceQueue` と `ObservationWorker`）

`anchors` を持つシナリオでだけ動くので、arena の既存シナリオの振る舞いは変わらない。

## 締切前に何が起きるか

**運用の設計に効く数字なので実測した。** 研究室の計算機（RTX 6000 Ada 2枚 / CUDA）、
`gemma4:latest`（Q4_K_M / 8.0B）、学生25人が同時に受験。

| | 実測 |
| --- | ---: |
| 全体 | 843秒 |
| 1人が終わるまで | 663〜843秒（11〜14分） |
| 学生の平均待ち | 58.1秒 |
| 学生の最長待ち | 172.9秒 |
| 代替値の採点 | 0人 |
| 順番待ちで断られた人 | 0人 |
| 所見づくりの失敗 | 0件 |

推論1回あたりは、質問づくり5.21秒・採点14.62秒・所見6.29秒。
学生1人あたり、経路上（接続確認1＋質問10＋採点1）で **67秒の GPU 時間**。
所見8件が背後でさらに50秒。

`67.2秒 × 25人 ÷ 並列2 = 840秒`。**実測843秒とほぼ一致するので、
待ち時間は素直に人数に比例する。**

### 100人でどうなるか

| | GPU 時間 |
| --- | ---: |
| 学生が待つ経路 | **約56分** |
| 所見（背後） | 約42分 |

**提出期間を数日取れば問題にならない。** 学生がいつ提出しても、必要な GPU 時間の
合計は変わらず、散っていれば1人の体感は数分で済む。

**同時受験は25人までなら1人14分**で、案内している「所要15〜25分」に収まる。
50人を超えると案内と食い違うので、そのときは

- 提出期間を数日取る（本筋）
- 締切を回ごとにずらす
- 案内に「締切直前は時間がかかります」と書く

### この数字に至るまでに踏んだ落とし穴

同じ構成で **1211秒かかっていた時期がある。** 原因は2つとも、測らないと
気づけないものだった。

- **Ollama が Vulkan を選んでいた。** NVIDIA のカードでも CUDA と Vulkan の
  両方を見つけて Vulkan を選ぶことがある。`nvidia-smi` では両カードが75%で
  回っているので、GPU が使われていることを確かめても気づけない。
  生成速度は CUDA の5〜6分の1だった。`OLLAMA_VULKAN=0` で直る
- **`think: false` を渡していなかった。** `gemma4` は思考に1233字を使ってから
  本文108字を書く。生成の上限に達すると本文が空で返り、所見が黙って落ちる

**計算機や設定を変えたら測り直すこと。** 上の数字も、この2つを直す前は
すべて過大だった。

## 実行環境

研究室の計算機（RTX 6000 Ada 2枚）で運用する。

カードごとに Ollama を立て、arena には口を2つ渡す。1台の大きな GPU に
見せかけて層を分割すると、1枚に収まるモデルでもかえって遅くなるため。
`gemma4:latest`（Q4_K_M / 8.0B）は VRAM 4.2 GB なので、48 GB のカード1枚に余裕で載る。
設定は arena 側の README を参照。

起動時の環境変数はこの4つ。**`OLLAMA_VULKAN=0` を忘れると桁が変わる。**

```bash
CUDA_VISIBLE_DEVICES=0 OLLAMA_HOST=127.0.0.1:11434 \
  OLLAMA_VULKAN=0 OLLAMA_KEEP_ALIVE=-1 OLLAMA_CONTEXT_LENGTH=8192 ollama serve &
```

`OLLAMA_KEEP_ALIVE=-1` は常駐のため。既定では5分アイドルでモデルが VRAM から
降り、次の推論が読み込み待ちを含む。測定値がぶれるうえ、締切前に間欠的な
引っかかりになる。`OLLAMA_CONTEXT_LENGTH` を指定しないと、モデルの上限
（gemma4 は131072）を確保して KV キャッシュが無駄に大きい。

CUDA で動いているかはログでしか分からない。

```bash
grep -E "selecting GPU backend|inference compute" /tmp/ollama0.log
```

計算機を替えたら測り直すこと。

```bash
python3 tools/crunch.py --base http://<研究室の計算機>:8000 --students 12
```

読み方が2つある。

- **`✗ N人が代替値で採点された`** — これが不味い。推論が制限時間を超え、
  採点が字数から出した数字に落ちている。並列数か制限時間を見直す
- **`△ N人が断られた`** — こちらは設計どおり。混みすぎたら劣化させずに断る。
  画面は自動で出し直すので、少数なら実害はない

締切が同時に集中したときに捌けるかは、この実測で決める。
足りなければ、締切を回ごとにずらす。

## まだ無いもの

- **学生の同定** — 学籍番号と氏名は入力欄があるだけで、本人確認にはならない。
  学認（Shibboleth）連携が本筋
- **学生間の類似度検出** — 同じ答えが並んでいないかを見る
- **個人情報の取扱いと評価の位置づけの文書化** — 学内の確認に回すもの

シナリオの所見の質は、第1回と第12回でしか人の目で確かめていない。
残り11回は機械的な検査だけである。

## モデル選定

`gemma4:latest` を選んだ。8モデルを、質の違う3つの回答で比較した結果。

| モデル | サイズ | 速度 | 引用の実在 | 備考 |
| --- | ---: | ---: | ---: | --- |
| **gemma4:latest** | 9.6 GB | 4.1–7.1秒 | 12/12 | 判別が明快 |
| qwen3.6:35b-a3b | 23 GB | 6.3–21.9秒 | 12/12 | 判定が厳しめ |
| gemma3:12b | 8.1 GB | 7.9–10.2秒 | 11/12 | 中位と下位の判別が弱い |
| gemma3:27b | 17 GB | 16.5–20.1秒 | 11/12 | 27B でも上と同じ弱点 |
| gpt-oss:20b | 13 GB | 23.8–39.0秒 | 10/12 | 薄い回答を高く評価する |
| llama4:latest | 67 GB | 13.9–43.6秒 | 10/12 | 遅く、重い |
| llama3.3:latest | 42 GB | 29.5–54.4秒 | 4/12 | 引用を多く捏造する |
| qwen3.6:35b-mlx | 21 GB | — | — | JSON スキーマ非対応 |

注意点が3つある。

- **Ollama の JSON スキーマ強制を使うこと。** 使わないと qwen と llama4 は
  JSON を壊す。プロンプトだけで形式を指示しても守られない
- **gpt-oss は思考チャネルに3,700字を費やす。** `num_predict` を 4,000 以上に
  しないと本文が空になる
- サイズと質は比例しない。gemma3 は 12B でも 27B でも同じ弱点を示した

**第二意見が要る場合は `qwen3.6:35b-a3b`。** gemma3 は gemma4 と同系統で
癖が似ており、食い違いを拾いにくい。

この比較は1問・3回答での結果である。実データで再評価すること。
